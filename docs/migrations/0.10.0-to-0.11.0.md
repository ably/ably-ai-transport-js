# Migrate from 0.10.0 to 0.11.0

## Why 0.11.0 changes

In 0.10.0, the transport sat between your application and the Ably channel. It resolved the channel from your client, owned its options, attached and detached it, and delivered each message to your subscribe handler. Your application could not use the channel the way it uses any other Ably channel, and the transport had to grow an option for every channel feature an application wanted.

0.11.0 implements [AITRFC-032](https://ably.atlassian.net/wiki/spaces/AI/pages/5536645151). Your application holds the channel through the Ably Pub/Sub SDK, and AI Transport supplies two helpers that work on that channel:

- **An agent adaptor** publishes a provider's events on a channel you give it. It takes the place of the transport's `send` and `pipe`.
- **A decoder** turns each message your own `channel.subscribe` handler receives, live or from history, back into the provider's events. It takes the place of the transport's `subscribe` and `history`.

The codecs do not change their rows, but they no longer hold state. The decoder holds the state that a streaming reader needs.

0.11.0 also moves AI Transport onto version 3 of the Ably Pub/Sub SDK, which replaces the `ably` package with one client package for each side of the connection. Move your packages first, as [Move to the Ably Pub/Sub v3 packages](#move-to-the-ably-pubsub-v3-packages) describes, then move from the transport to an adaptor and a decoder.

## Upgrade the client and the agent together

The wire format changes. Every message a codec writes now carries the codec's `name`, `ai` for the shipped codecs, and the codec's id under `extras.ai.codec`, and a decoder skips any message without both. A 0.11.0 decoder therefore ignores messages that a 0.10.0 agent published, and an AG-UI message that 0.10.0 named `ag-ui` is now named `ai`. Deploy the agent and the clients together, and expect history written by 0.10.0 to decode with no events.

## Move to the Ably Pub/Sub v3 packages

Pub/Sub v3 no longer publishes the `ably` package. It ships one client package for each side of the connection:

| Your code runs on                                                                | Install               |
| :------------------------------------------------------------------------------- | :-------------------- |
| Infrastructure you operate: a Node.js server, a container, a serverless function | `@ably/pubsub-server` |
| An end user's device: a browser, React Native, Electron, a mobile or desktop app | `@ably/pubsub-device` |

Your agent belongs on `@ably/pubsub-server` and your clients on `@ably/pubsub-device`. The [ably-js v3 migration guide](https://github.com/ably/ably-js/blob/main/docs/migration-guides/v3/lib.md#what-declaring-a-side-means) explains what declaring a side means.

AI Transport itself declares no side. An adaptor and a decoder work on a channel from a client of either package.

| 0.10.0                                                     | 0.11.0                                                                            |
| :--------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| `ably` peer dependency                                     | `@ably/pubsub-server` or `@ably/pubsub-device`, both optional peers               |
| `new Ably.Realtime(options)` on the agent                  | `createRealtimeClient(options)` from `@ably/pubsub-server`                        |
| `new Ably.Realtime(options)` on the client                 | `createClient(options)` from `@ably/pubsub-device`                                |
| `new Ably.Rest(options)`, for example in a token endpoint  | `createHttpClient(options)` from `@ably/pubsub-server`                            |
| `AblyProvider` from `ably/react`                           | `PubSubClientProvider` from `@ably/pubsub-device/react`                           |
| `useAbly()`, `useChannelStateListener()` from `ably/react` | `usePubSubClient()`, `useChannelStateListener()` from `@ably/pubsub-device/react` |
| `Ably.ErrorInfo` from `ably`                               | `ErrorInfo` from `@ably/pubsub-server` or `@ably/pubsub-device`                   |

### Update the packages

Remove `ably` and install the Pub/Sub package for each side. In a repository that holds both an agent and a client, install each package where that code runs.

```sh
npm uninstall ably

npm install @ably/ai-transport@0.11.0 @ably/pubsub-server   # in your agent
npm install @ably/ai-transport@0.11.0 @ably/pubsub-device   # in your client
```

The peer dependencies change:

- `ably` is no longer a peer.
- `@ably/pubsub-server` and `@ably/pubsub-device` are new optional peers. Install the one for the side your code runs on.
- `@ably/pubsub-core` is a dependency of AI Transport and of both Pub/Sub packages, and is installed for you. Don't add it to your own dependencies or import from it.
- `ai`, `openai` and `@ag-ui/core` keep the same ranges. `react` is no longer a peer, because the React entry point is removed.

### Create the agent's client with `createRealtimeClient`

```js
// 0.10.0
import * as Ably from 'ably';
const ably = new Ably.Realtime({ key: process.env.ABLY_API_KEY });

// 0.11.0
import { createRealtimeClient } from '@ably/pubsub-server';
const pubsubClient = createRealtimeClient({ key: process.env.ABLY_API_KEY });
```

A token endpoint that signs token requests changes the same way, from `new Ably.Rest({ key })` to `createHttpClient({ key })` from `@ably/pubsub-server`.

> [!WARNING]
> **Token authentication on the agent.** If your agent authenticates with `authUrl` or `authCallback` rather than an API key, Ably accepts a server-side client only when its token carries the signed `x-ably-clientType=server` claim, and rejects the connection otherwise. Add the claim to the tokens your auth service issues for the agent before you deploy. With an API key, nothing changes. See [With token authentication, you must add a claim](https://github.com/ably/ably-js/blob/main/docs/migration-guides/v3/lib.md#server-token-auth).

### Create the client's client with `createClient`

```js
// 0.10.0
import * as Ably from 'ably';
const ably = new Ably.Realtime({ authUrl: '/api/auth/token' });

// 0.11.0
import { createClient } from '@ably/pubsub-device';
const pubsubClient = createClient({ authUrl: '/api/auth/token' });
const channel = pubsubClient.channels.get(channelName);
```

On an Ably account billed by monthly active users, a device connection must carry a client ID, and is rejected at connect without one. Set `clientId`, or issue tokens that carry one.

### Move the React providers

Mount `PubSubClientProvider` in place of `AblyProvider`, and take `ChannelProvider` and the channel hooks from `@ably/pubsub-device/react`. A v2 `AblyProvider` and a v3 `PubSubClientProvider` don't share a React context, so move the provider and every Pub/Sub hook in the tree together. Inside the tree, `useAbly()` becomes `usePubSubClient()`. `useChannelStateListener`, `useChannel` and `usePresence` keep their names. The `ablyId` prop and option become `contextId`.

### Update type annotations

The Pub/Sub client classes are gone in v3, so a type annotation that named one uses the client interface instead:

| 0.10.0                                 | 0.11.0                                                                                          |
| :------------------------------------- | :---------------------------------------------------------------------------------------------- |
| `Ably.Realtime`, `Ably.RealtimeClient` | `PubSubRealtimeClient` from `@ably/pubsub-server`, or `PubSubClient` from `@ably/pubsub-device` |
| `Ably.Rest`, `Ably.RestClient`         | `PubSubHttpClient` from `@ably/pubsub-server`                                                   |

### Your own Pub/Sub code

Pub/Sub v3 has breaking changes of its own that your application may hit, for example:

- The `environment`, `restHost` and `realtimeHost` client options are removed, and v3 silently ignores them. Use `endpoint`.
- `channels.release()` throws unless the channel is detached first.
- On the web and React Native, `useBinaryProtocol: true` needs the `MsgPack` plugin from `@ably/pubsub-device/msgpack`.
- Node.js 22 or later is required, as it already is for AI Transport.

The [ably-js v3 migration guide](https://github.com/ably/ably-js/blob/main/docs/migration-guides/v3/lib.md) lists every change.

### Loading AI Transport from a script tag

Load the Pub/Sub v3 bundle, `https://cdn.ably.com/lib/ably.min-3.js`, in place of `ably.min-2.js`. It is exposed as the global `AblyPubSub` rather than `Ably`, and its `createClient` builds the client whose channel you hand to an adaptor or subscribe a decoder to.

```diff
- <script src="https://cdn.ably.com/lib/ably.min-2.js"></script>
+ <script src="https://cdn.ably.com/lib/ably.min-3.js"></script>
- const client = new Ably.Realtime({ authUrl: '/api/auth/token' });
+ const client = AblyPubSub.createClient({ authUrl: '/api/auth/token' });
  const codec = AblyAiTransport.defineCodec({ id: 'my-format', typeOf: (e) => e.type, events: { /* one row per event type */ } });
  const decoder = AblyAiTransport.createDecoder(codec);
  client.channels.get(channelName).subscribe(decoder.receive);
```

The AI Transport bundle carries the core entry point only, so a page that loads it from a script tag builds its codec with `defineCodec`. The Vercel, OpenAI and AG-UI adaptors and decoders need a bundler.

## What replaces each transport API

| 0.10.0                                                            | 0.11.0                                                                                                         |
| :---------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `createTransport({ client, channelName, codec })`                 | `client.channels.get(channelName)`, then an adaptor and a decoder on it                                        |
| `transport.send(event, { headers })`                              | `adaptor.send(event, { headers })`                                                                             |
| `transport.pipe(source, { signal, headers })`                     | `adaptor.pipe(source, { signal, headers })`, or `adaptor.pipeEach` to act on each event                        |
| `transport.subscribe(handler)`                                    | `decoder.onEvent(handler)` and `channel.subscribe(decoder.receive)`                                            |
| `transport.history({ limit })`                                    | `channel.history({ untilAttach: true, limit })`, each message through `decoder.decode`                         |
| `subscribe(handler, { history: { replay: fromSerial(serial) } })` | Rewind the channel to the serial; see below                                                                    |
| `untilEvent(predicate)`                                           | A loop over `channel.history`, stopping where your predicate matches                                           |
| `transport.on('error', handler)`                                  | `decoder.onError(handler)`                                                                                     |
| `transport.on('discontinuity', handler)`                          | `channel.on(handler)` on the channel itself; see below                                                         |
| `transport.close()`                                               | `channel.unsubscribe(decoder.receive)`; the adaptor holds nothing to close                                     |
| `createTransport({ codec: vercel })`                              | `vercelAdaptor(channel)` and `vercelDecoder()`                                                                 |
| `createTransport({ codec: openai })`                              | `openaiAdaptor(channel)` and `openaiDecoder()`                                                                 |
| `createTransport({ codec: agui })` or `createAGUICodec()`         | `agUiAdaptor(channel)` and `agUiDecoder()`                                                                     |
| A custom codec passed to `createTransport`                        | `createAgentAdaptor(channel, codec)` and `createDecoder(codec)`                                                |
| `channelModes`, `OBJECT_MODES` and `echoMessages`                 | Channel options you pass to `channels.get` yourself                                                            |
| `@ably/ai-transport/react`                                        | `<PubSubClientProvider>` and `<ChannelProvider>` from `@ably/pubsub-device/react`, with a decoder in an effect |

## Move the agent to an adaptor

```typescript
// 0.10.0
const transport = createTransport({ client: ably, channelName, codec: vercel });
try {
  await transport.pipe(stream, { signal, headers });
} finally {
  await transport.close();
}

// 0.11.0
const adaptor = vercelAdaptor(pubsubClient.channels.get(channelName));
await adaptor.pipe(stream, { signal, headers });
```

`pipe` keeps its contract. It resolves with the serial of its last publish, it rejects with `OperationCancelled` or `PipeFailed`, and it flushes and repairs what it wrote before it settles. An adaptor can also carry default headers, `vercelAdaptor(channel, { headers })`, which a call's headers override.

`pipeEach` is new. It hands each event back once it is written, with the serial of the message the event landed on:

```typescript
for await (const { event, serial } of adaptor.pipeEach(stream, { signal })) {
  if (event.type === 'finish') await db.saveReplySerial(serial);
}
```

`pipeEach` flushes and repairs like `pipe` however the loop ends, the source ending, a failure, the signal, or leaving the loop early. A stop writes no closing message, so a client sees a stream that was cut off stay open. A `ReadableStream` source is released, not cancelled, so stop the model call yourself if it should stop too.

## Move the client to a decoder

```typescript
// 0.10.0
const transport = createTransport({ client: ably, channelName, codec: vercel });
const unsubscribe = transport.subscribe(apply);
transport.on('error', report);

// 0.11.0
const channel = pubsubClient.channels.get(channelName);
const decoder = vercelDecoder();
decoder.onEvent(apply);
decoder.onError(report);
await channel.subscribe(decoder.receive);
// later: channel.unsubscribe(decoder.receive)
```

A delivery is still `{ event, message }`, and every message still comes back as at least one delivery. A message that is not the codec's comes back with `event: undefined`. Use one decoder per channel, and pass it both the live messages and the history messages, so that it decodes a message of an open stream that both carry only once. Once a stream's closer has been decoded, the decoder forgets the stream, so either decode history before live messages, holding the live deliveries until history is done, since `untilAttach` needs the channel attached and subscribed first, or rewind the channel to a serial so one subscription delivers both in order.

The transport attached the channel on the first `subscribe` and detached it on `close`. The Pub/Sub SDK does the same when you call `channel.subscribe` on a channel from `channels.get`, and you decide when to detach. Under `<ChannelProvider>` from `@ably/pubsub-device/react`, subscribe does not attach, so call `channel.attach()` yourself after subscribing.

The transport reported a discontinuity when the channel went FAILED, SUSPENDED or DETACHED, or reached ATTACHED or UPDATE with `resumed: false`. Watch for the same state changes with `channel.on`. To catch up, read your store again, detach the channel, and rewind it to the serial the store returns with `channel.setOptions({ params: { rewind } })`, as the next section describes. `demo/minimal` does this whenever its channel loses continuity.

## Catch up with rewind to a serial

`fromSerial` and `untilEvent` are removed. To catch up from a serial your store holds, rewind the channel to it when you get the channel:

```typescript
const channel = pubsubClient.channels.get(
  channelName,
  stored.serial === undefined ? undefined : { params: { rewind: stored.serial } },
);
const decoder = vercelDecoder();
decoder.onEvent(apply);
await channel.subscribe(decoder.receive);
```

Set the param on the first `channels.get` for the channel. For a channel that is already attached, `channels.get` with a different `rewind` throws, and `channel.setOptions` is the call that changes it.

On attach, the platform delivers every message after the serial, then live messages, in channel order, so the decoder sees each message once and in order. The serial's own message is not replayed. A message that was appended to arrives first as one full-content update. Rewind delivers at most 1,000 messages after the serial, and applies only when the channel attaches. `demo/minimal/src/app/page.tsx` and `chat.tsx` are the full version.

## Replace the React entry point

`@ably/ai-transport/react` is removed, with `TransportProvider`, `useTransport`, `useDeliveries`, `useHistory` and `useTransportStatus`. Mount `<PubSubClientProvider>` and `<ChannelProvider>` from `@ably/pubsub-device/react`, get the channel from the client, and in an effect subscribe a decoder and then call `channel.attach()`, since `<ChannelProvider>` turns off attach on subscribe. `useChannelStateListener` from `@ably/pubsub-device/react` reports the channel's state.

## Update codec code

- `Codec.adapterTag` is now a required `id`, and `defineCodec` takes `id` in place of `adapterTag`.
- `Codec` gains a required `name`, the message name the codec writes on every message and a decoder filters on. `defineCodec` takes `name` for the whole codec, defaulting to `ai`; a row can no longer name its own message, and `defineCodec` no longer takes `logger`.
- A hand-written codec must write its `name` as the message name and its `id` under `extras.ai.codec` on every message it encodes, appends included.
- A built codec no longer holds a decoder core, so calling `codec.decode` directly gives you no tail reduction and no replay guard. Use `createDecoder(codec)` for that.
- `createDecoderCore` and its types `DecoderCore` and `DecoderCoreOptions` are no longer exported.
- `vercel`, `createVercelCodec`, `openai`, `createOpenAICodec`, `agui` and `createAGUICodec` are no longer exported. Use the provider's adaptor and decoder factories.

## Attribution

The transport registered an Ably-Agent entry when it resolved the channel from your client. An adaptor receives a channel and never sees the client, so 0.11.0 sends no Ably-Agent attribution.
