# Migrate from 0.9.0 to 0.10.0

## Why 0.10.0 changes so much

AI Transport 0.9.0 did three jobs. It streamed agent output to clients, it managed a run lifecycle for sending prompts, cancel messages and steering messages to the agent, and it stored the conversation for you through durable sessions. Most applications already have a database that holds the conversation, and a request path (an HTTP route, a workflow signal or a queue) that validates, authorizes and logs input before it reaches the agent. This meant with 0.9.0 you often had two copies of the conversation and two ways for input to reach the agent, and you had to keep them in sync.

0.10.0 simplifies adoption by focusing only on the first job: delivering agent output to every connected client reliably while the agent is working.

## How the pieces fit together in 0.10.0

- **Agent output goes through AI Transport.** Your agent still pipes the model's event stream to an Ably channel through the codec.
- **You control the message format.** The codecs manage streaming of agent output events over the channel, but all other messages sent on the channel are fully defined and controlled by your application code.
- **Clients receive messages live and recover from disconnects.** When a client reconnects, reloads or joins from another device in the middle of a response, it replays the channel from a known point and carries on live, as long as that point is within your channel's retention window.
- **Your application stores the conversation.** Clients load completed history from your store, then use the channel to catch up on the response that's still in progress.
- **Input goes through your own request path.** Prompts, cancel messages and steering messages reach the agent the same way your other application requests do. If multiple devices or users need to see that input, you can optionally publish a copy to the channel.

## What has changed

Every 0.9.0 application needs code changes to move to 0.10.0:

- **Wire format.** 0.10.0 can't decode messages published by 0.9.0, so deploy your client and agent together. If you've written your own decoder against the 0.9.0 wire format, for example on a platform without a JavaScript SDK, you'll need to update it as well.
- **Conversation tree.** If you relied on the SDK to rebuild the conversation, handle branching or apply optimistic updates, that logic moves into your application. Clients still get a live, resumable experience; the change is that the SDK no longer holds the conversation for you.
- **Runs and steps.** Lifecycle events are replaced by your own IDs in message headers. Cancel messages and steering messages go through your own route, or through your own message on the channel.

> [!WARNING]
> **Breaking change: wire format.** The 0.10.0 wire format is not backwards compatible. A 0.10.0 codec cannot decode the messages that 0.9.0 published. Read [Upgrade the client and the agent together](#upgrade-the-client-and-the-agent-together) before you deploy 0.10.0.

> [!WARNING]
> **Breaking change: durable sessions.** 0.10.0 removes durable sessions. If your application uses `createClientSession`, `createAgentSession`, `withAgentSession` or the hooks in `@ably/ai-transport/vercel/react`, read [Durable sessions are removed](#durable-sessions-are-removed) before you upgrade.

## What replaces each 0.9.0 API

| 0.9.0                                                                                                              | 0.10.0                                                                                                           |
| :----------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| `createClientTransport`, `createAgentTransport`                                                                    | `createTransport`, the same function on the client and the agent                                                 |
| `createUIMessageCodec()`, `createUIMessageSessionCodec()`                                                          | `vercel` or `createVercelCodec()` from `@ably/ai-transport/vercel`                                               |
| `ResponsesCodec`, `ResponsesSessionCodec`                                                                          | `openai` or `createOpenAICodec()` from `@ably/ai-transport/openai`                                               |
| `publishInput()`                                                                                                   | The prompt in the request that wakes the agent, or `send()`, which resolves with `{ serial }`                    |
| `openRun()`, `run.pipe()`, `run.end()`                                                                             | `pipe(source, { signal, headers })`, which resolves with `{ serial }`                                            |
| `locateInput(eventId)`                                                                                             | The prompt in the request that wakes the agent, or a `subscribe()` replay with `untilEvent`                      |
| `transport.cancel(runId)`, `run.abortSignal`                                                                       | Your own route, or your own cancel message on the channel, and the agent aborts the signal it passed to `pipe()` |
| Run and step lifecycle events                                                                                      | Removed. Your own ids in the headers of `send()` and `pipe()`                                                    |
| `steer()`                                                                                                          | Removed. Your own messages on the channel                                                                        |
| `pageUntilLocated`, `TransportHistoryOptions.onPage`                                                               | `subscribe(handler, { history: { replay } })` with `fromSerial` or `untilEvent`, and `history()`                 |
| Durable sessions: `createClientSession`, `createAgentSession`, `withAgentSession`, views and the conversation tree | Removed, and your application stores the conversation                                                            |
| `@ably/ai-transport/vercel/react`: `useChatTransport`, `useMessageSync`, `ChatTransportProvider`                   | Removed. `TransportProvider` and the hooks in `@ably/ai-transport/react`                                         |
| `@ably/ai-transport/temporal`, `@ably/ai-transport/temporal/workflow`                                              | Removed                                                                                                          |
| `RunResponseStreamFailed` (104008)                                                                                 | `PipeFailed` (104008)                                                                                            |

## Upgrade the client and the agent together

A 0.9.0 client and a 0.10.0 agent cannot share a channel, so you need to deploy the client and the agent together, or handle the migration between the SDK versions manually.

A channel that 0.9.0 published to keeps its 0.9.0 messages until your retention window ends, and a 0.10.0 client that replays the channel receives the messages but cannot decode them into SDK events.

Version 0.10.0 is built around the conversation remaining in your own database. Message retention on the channel is not changed between 0.9.0 and 0.10.0, but the APIs in 0.10.0 are designed around your database storing the conversation, and the channel being used for live delivery and recent-history catchup.

## Update the package

```sh
npm install @ably/ai-transport@0.10.0
```

The peer dependencies change:

- `@ag-ui/core` is a new optional peer, for the AG-UI codec.
- `@temporalio/activity`, `@temporalio/worker` and `@temporalio/workflow` are no longer peers, because the Temporal entry points are removed.
- `ably`, `ai`, `openai` and `react` keep the same ranges.

## Replace the codec

Each codec ships as a ready-made codec instance export and as a factory. You can pass the instance to `createTransport`, or call the factory for a codec typed with your own message types, such as the AI SDK's `UIMessage` type parameters.

| 0.9.0                                                                    | 0.10.0                                                              | Entry point                 |
| :----------------------------------------------------------------------- | :------------------------------------------------------------------ | :-------------------------- |
| `createUIMessageCodec()`, `createUIMessageSessionCodec()`                | `vercel`, `createVercelCodec()`                                     | `@ably/ai-transport/vercel` |
| `ResponsesCodec`, `ResponsesSessionCodec`                                | `openai`, `createOpenAICodec()`                                     | `@ably/ai-transport/openai` |
| No AG-UI support                                                         | `agui`, `createAGUICodec()`                                         | `@ably/ai-transport/ag-ui`  |
| `defineCodec` with input and output descriptors, returning a `WireCodec` | `defineCodec` with one row for each event type, returning a `Codec` | `@ably/ai-transport`        |

## Move the agent to `pipe()`

Your 0.10.0 agent can read the prompt from the HTTP request, create a transport, and pipe the model's output to the channel. The transport does not have a `connect()` method. `send()` and `pipe()` do not need the channel attached, because the transport does not subscribe to the channel by default. The first `subscribe()` call automatically attaches to the channel.

0.9.0:

```js
const transport = createAgentTransport({
  client: ably,
  channelName: conversationId,
  codec,
  clientId: 'agent',
});
await transport.connect();

const trigger = await transport.locateInput(eventId);
const prompt = trigger?.inputs.find((input) => input.kind === 'message');
const run = transport.openRun({ input: trigger });

const result = streamText({
  model,
  messages: await convertToModelMessages([...history, prompt.payload]),
  abortSignal: run.abortSignal,
});

const { reason } = await run.pipe(result.toUIMessageStream());
await run.end({ reason });
transport.close();
```

0.10.0:

```js
import { createTransport } from '@ably/ai-transport';
import { vercel } from '@ably/ai-transport/vercel';

const { channelName, message } = await req.json();
const transport = createTransport({ client: ably, channelName, codec: vercel });

const result = streamText({
  model,
  messages: await convertToModelMessages([...history, message]),
  abortSignal: req.signal,
});
const { serial } = await transport.pipe(toUIMessageStream({ stream: result.fullStream }), {
  signal: req.signal,
  headers: { requestId: message.id },
});
await transport.close();
```

- `pipe()` resolves with the serial of the last message it published. Your agent can store the serial with the response, so a client can replay the channel from it.
- `pipe()` rejects with `OperationCancelled` when its signal aborts, and with `PipeFailed` when a publish fails.
- `createTransport` does not take a `clientId`. The transport publishes as the Ably client you pass it.

## Move the client to `subscribe()`

Your 0.10.0 client can put the prompt in the HTTP request to the agent. The client receives each message on the channel as a delivery, which is a pair of the decoded event and the Ably message that event was decoded from. Your client needs to merge the events with your provider's own reducer, such as the AI SDK's `readUIMessageStream`.

0.9.0:

```js
const transport = createClientTransport({ client: ably, channelName: conversationId, codec });
transport.subscribe((event) => {
  if (event.kind === 'run-lifecycle') return setActiveRun(event.event);
  fold.apply(event);
});
await transport.connect();

const sent = await transport.publishInput({ kind: 'message', payload: message });
await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ conversationId, eventId: sent.eventId }),
});
```

0.10.0:

```js
const transport = createTransport({ client: ably, channelName, codec: vercel });
transport.subscribe(({ event, message }) => {
  if (event !== undefined) merge(event, message.extras?.headers?.requestId);
});

await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ channelName, message }),
});
```

Your client can also publish the prompt to the channel with `send()`, so the user's other devices receive it.

## Cancel a response with your own route or your own message

0.10.0 does not have a cancel message of its own, so it removes `transport.cancel(runId)` and `run.abortSignal`. Your agent can cancel a response by aborting the signal it passed to `pipe()`, and your client can ask it to in one of two ways:

- Your client can call your agent's HTTP endpoint, either by aborting the request that started the response or with a separate request, and your endpoint can handle the cancellation.
- Your client can publish a cancel message to the channel, in a format you own, and your agent can subscribe to the channel and handle the cancellation when the message arrives.

The codec does not recognise your cancel message, so the agent's subscribe handler receives it as a delivery with `event` set to `undefined`, and can read the raw Ably message:

```js
// Client code.
await ably.channels.get(channelName).publish('cancel', { requestId });

// Agent code.
const controller = new AbortController();
transport.subscribe(({ event, message }) => {
  if (event === undefined && message.name === 'cancel' && message.data?.requestId === requestId) {
    controller.abort();
  }
});
await transport.pipe(stream, { signal: controller.signal, headers: { requestId } });
```

A cancelled pipe rejects with `OperationCancelled`, and it does not publish the events that end the response. With the Vercel AI SDK codec, your agent can publish an `abort` chunk with `send()` if your clients wait for a `finish` chunk.

## Replace runs and steps with headers

0.10.0 does not publish run or step lifecycle events. The `headers` option on `send()` and `pipe()` goes on every message the call publishes, so you can tie a response to its prompt with a `requestId`, or a retry to its attempt with your own ids. A subscriber can read the headers from `message.extras.headers`.

0.10.0 removes the `getTransportHeaders`, `getCodecHeaders`, `mergeHeaders` and `buildTransportHeaders` helpers, and the `HEADER_*` and `EVENT_*` constants.

0.10.0 does not support steering. To send a steering message, you can publish your own message on the same channel, in the same way as a cancel message.

## Durable sessions are removed

0.10.0 removes durable sessions: `createClientSession`, `createAgentSession`, `withAgentSession`, `Invocation`, views, the conversation tree, and the `useChat` integration in `@ably/ai-transport/vercel/react`.

In 0.10.0 your application stores the conversation, and the channel carries the live messages for your retention window. Your application needs to do the work the session did:

| 0.9.0 durable sessions                                | In 0.10.0                                                                                                        |
| :---------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| The session rebuilt the conversation from the channel | Your client can load the conversation from your store, then replay the channel from its serial with `fromSerial` |
| The agent read the conversation from `run.view`       | Your agent can load the conversation from your store, and read the new prompt from the request that wakes it     |
| Conversations lasted as long as the channel kept them | Conversations last as long as your store keeps them                                                              |
| The conversation tree, branching and regeneration     | Your application can model branches and regenerated responses in your store                                      |
| Optimistic updates for the user's own messages        | Your client can add the user's message to its own list when it sends it                                          |
| Human-in-the-loop tool approvals through the session  | Your application can resolve tool calls and approvals from your provider's own events                            |

## Move to the React hooks in `@ably/ai-transport/react`

| 0.9.0                                                      | 0.10.0                                                  |
| :--------------------------------------------------------- | :------------------------------------------------------ |
| `ClientSessionProvider`, `ChatTransportProvider`           | `TransportProvider`, with a `channelName` and a `codec` |
| `useClientSession`, `useChatTransport`                     | `useTransport`                                          |
| `useAblyMessages`, `useMessageSync`, `useMessagesWithSeed` | `useDeliveries`, and your own merge                     |
| `useView`, `useCreateView`, `useTree`                      | Removed                                                 |
| None                                                       | `useHistory`, `useTransportStatus`                      |

0.10.0 does not ship a `ChatTransport` for the AI SDK's `useChat`. The Vercel AI SDK quickstart builds its chat component on `useTransport`.

## Replay history with `fromSerial` and `untilEvent`

0.10.0 removes `pageUntilLocated` and the `onPage` history callback. A subscription replays history before live messages when you pass a replay function:

```js
import { fromSerial, untilEvent } from '@ably/ai-transport';

// From a serial your store holds.
transport.subscribe(apply, { history: { replay: fromSerial(stored.serial) } });

// Back to an event you recognise.
transport.subscribe(apply, {
  history: { replay: untilEvent(({ event }) => event?.type === 'start') },
});
```

`history()` pages back through the channel without subscribing. A transport reports a gap in delivery on `on('discontinuity')`, and your client can subscribe again from the last serial it received.
