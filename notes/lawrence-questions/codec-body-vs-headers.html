Codec wire layout: body vs headers

How the OpenAI and Vercel codecs decide what goes in an Ably message's data (body) versus its codec headers (extras.ai.codec) — and why they look different while following the same rule.

Lawrence's question

"Why do some events (e.g. response.completed and response.output_item.done) have the full event in their JSON body, and others (e.g. response.content_part.done) just store a subset of the event's properties, and do so in the Ably message extras? Is this consistent with what the Vercel codec does?"

Asked while reviewing the OpenAI Responses codec (AIT-742) against the Vercel codec. This page is the answer.

data — message body (the payload) extras.ai.codec — codec headers (metadata) extras.ai.transport — transport tier (shown greyed; same on every message)

The one rule both codecs follow

Principal payload → body

data

The event's content — the thing the reducer folds into conversation state. The full provider object, a streamed text fragment, a tool's output, a file URL.

Metadata → headers

extras.ai.codec

Small bits used for dispatch, positioning, or reconstruction: the kind discriminator, ids, indices, flags. Usually scalars, but structured bits can ride as a JSON-stringified header (e.g. providerMetadata).

The split axis is payload vs metadata — not scalar vs object. Each codec applies this rule to its own wire types, which is why they end up looking different.

OpenAI Responses codec

response.completed OpenAI whole object → body
The whole Response snapshot is the payload — nothing to decompose, so it all sits in the body. Same shape for response.created / in_progress / output_item.added / output_item.done.
name: "ai-output"

extras.ai.codec {
  kind:   "response.completed"
  stream: "false"
}
data {
  id:     "resp_8f2…",
  object: "response",
  status: "completed",
  output: [ { type: "message", … } ],
  usage:  { input_tokens: 42, … },
  …                       // full snapshot
}
extras.ai.transport { run-id, invocation-id,
  codec-message-id, role, … }
response.content_part.done OpenAI subset → headers, no body
A boundary marker the reducer ignores. Declared only so the agent can republish it from history without tripping the "unsupported event" throw. Only its position scalars need to survive.
name: "ai-output"

extras.ai.codec {
  kind:          "response.content_part.done"
  stream:        "false"
  item_id:       "msg_abc"
  output_index:  "0"
  content_index: "0"
}
data ""  (empty — no payload)
extras.ai.transport { run-id, invocation-id,
  codec-message-id, role, … }
text (stream delta) OpenAI fragment → body, position → headers
The one streamed family. Each append carries only the new text fragment in the body; the positional metadata (output_index / content_index / part) rides on headers so it survives alongside the stream.
name: "ai-output"

extras.ai.codec {
  kind:          "text"
  stream:        "true"
  status:        "streaming"
  stream-id:     "msg_abc"   // = item_id
  item_id:       "msg_abc"
  output_index:  "0"
  content_index: "0"
}
data "Hello"   // just this delta's text
extras.ai.transport { run-id, invocation-id, … }
Why whole-object-in-body here? OpenAI
The shape of the OpenAI wire types drives it.
TMessage = a turn's raw OpenAI items.
The reducer wants those Response / ResponseOutputItem
objects back whole, and the transport never
dispatches or positions on anything inside them.

So there is no flat metadata worth promoting to
headers — the object is the payload, and it goes
in the body intact.

The only OpenAI event that is pure metadata
(content_part.done) is exactly the one that
goes headers-only.

Vercel AI SDK codec

tool-output-available Vercel split: ids → headers, output → body
Vercel chunks are flat bags of named fields, and the transport keys off individual ones — so each event is decomposed: identifiers/flags to headers, the variable content to the body.
name: "ai-output"

extras.ai.codec {
  kind:             "tool-output-available"
  stream:           "false"
  toolCallId:       "call_1"
  dynamic:          "false"
  providerExecuted: "false"
  preliminary:      "false"
}
data {
  output: { temperature: 14, unit: "C" }
}
extras.ai.transport { run-id, invocation-id, … }
tool-approval-request Vercel scalars only → headers, no body
The Vercel twin of content_part.done: the whole event is a couple of scalar identifiers, nothing downstream reads more, so it's headers-only with an empty body.
name: "ai-output"

extras.ai.codec {
  kind:       "tool-approval-request"
  stream:     "false"
  toolCallId: "call_1"
  approvalId: "appr_1"
}
data ""  (empty — no payload)
extras.ai.transport { run-id, invocation-id, … }

The same decision, side by side

Event Codec What it carries Body Headers
response.completed OpenAI whole Response snapshot (the payload) full object kind only
response.output_item.done OpenAI whole ResponseOutputItem (the payload) full object kind only
text (stream) OpenAI text fragment + position delta text id + indices
response.content_part.done OpenAI position scalars only (reducer ignores it) empty subset
tool-output-available Vercel tool output + ids/flags output ids + flags
file Vercel file URL + media type url mediaType + meta
tool-approval-request Vercel identifier scalars only empty ids

So are they consistent?

Yes — same rule, different-shaped inputs. Both put the principal payload in the body and metadata in extras.ai.codec. Header-only events exist in both (content_part.done ↔ tool-approval-request) for the same reason: their whole meaning is a few scalars.

The one honest divergence: Vercel always decomposes a chunk into typed fields + a small content body, because its chunks are flat and the transport reads individual fields. OpenAI sometimes ships a provider object whole in the body, because TMessage is "a turn's raw OpenAI items" — the object is the atom, and nothing keys off its internals.

That's a consequence of the two providers' wire types, not a contradiction of the framework — both data and fields are first-class knobs the descriptor model offers, and each codec reaches for whichever fits its types.
