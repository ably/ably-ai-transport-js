Transport data model — the grounding note

One mental model underneath all the codec/event detail. Four nested levels, a handful of ids, and one seam that lets a single codec hold either one message per turn (OpenAI today) or many (Vercel). Read this when the event docs make you feel lost — it's the map they hang off.

1The four levels

Every client rebuilds the conversation as this nesting. The generic transport owns the top two levels; the codec owns the bottom two. Read top-to-bottom: each level contains the one below.

Tree
The whole conversation — every node, from live messages and history. One per client session. Single source of truth.
generic transport
Node
One conversation step. An assistant reply (a run, keyed by runId) or a user input (keyed by codecMessageId). Owns exactly one Projection.
generic transport
Projection = codec's TProjection
The codec's private accumulator for that node. Built by init() then repeated fold(state, event, meta). Internal — not public API.
codec (internal)
Message(s) = CodecMessage<TMessage>
What getMessages(projection) returns — a list, each tagged with a codecMessageId. OpenAI: exactly one. Vercel: one or many. This is the public surface.
public API
Items / parts = TMessage
The message's content. OpenAI: a turn's ordered items (reasoning, function_call, function_call_output, message), each named by its item_id. Vercel: a UIMessage's parts.
codec domain type
The one place people go wrong: there is no single global projection. Each node has its own. So "everything squashes into one message" is only ever true within one node — and only for codecs (like OpenAI) that choose one message per node. Separate replies are separate nodes with separate projections, always.
2Who mints each id, and what it routes

Four identifiers do all the routing. The trick is that they live at different levels and are minted by different parties — keeping them straight dissolves most of the confusion.

idminted byscope / uniquenesswhat it routes
runId the agent, when a run starts one per assistant reply Keys a run node in the Tree. Every output event of that reply routes to this node's projection.
codecMessageId the message's author: the client for a user input; the agent per run.pipe() (crypto.randomUUID()) for an assistant reply. A codec may override it per-message on the wire (Vercel stamps a fresh one per start chunk). one per authored message Correlates a message across its lifecycle. Keys a user-input node; and distinguishes multiple messages within one run's projection (the Vercel case). Reaches the reducer as meta.messageId. Not the triggering user message's id — that rides separately as inputCodecMessageId for parent threading.

3The seam: one message per node, or many

The only structural difference between the OpenAI and Vercel codecs is how many messages a projection holds. The transport contract is identical for both — getMessages returns a list, and fold gets meta.messageId per event. OpenAI is the N=1 case; Vercel is the N>1 case.

OpenAI — N = 1
one run = one turn = one codecMessageId
OpenAIProjection {
  role
  items[]              // the turn's items
  byItemId: Map        // item_id → item
  codecMessageId       // a single scalar
}
getMessages() → [ one turn ]

The agent merges the whole agentic loop (all the /responses calls) into one output stream and calls run.pipe once → one crypto.randomUUID() stamped on every item → one message. Correct today, because a run genuinely is one assistant turn.

Vercel — N > 1
a run may carry several codecMessageIds
VercelProjection {
  messages: CodecMessage[]   // a LIST…
  trackers: Map              // …keyed by codecMessageId
  pendingToolResolutions[]
}
getMessages() → [ msg_a, msg_b, … ]

The piped AI-SDK stream carries multiple start chunks, and the codec stamps a distinct messageId per start — so one pipe emits several codecMessageIds. Each event routes to ensureMessage(state, codecMessageId) (find-or-create, then write). "Correlates strictly on codecMessageId."

OpenAI's single message is the N=1 specialisation of the same shape — not a shortcut that blocks the future. If OpenAI ever needs multiple messages per run (say, modelling commentary vs final_answer as separate messages), the trigger is "the agent stamps more than one codecMessageId in a run," and the reducer grows into the Vercel shape. Because OpenAIProjection is internal and getMessages already returns the list-shaped public type, that change breaks nothing downstream and needs no core change.
3bClient-side tools: the concrete way one node gets many messages

A client-side tool call is the cleanest real example of N>1. The whole thing stays in one run node (the run is reused across suspend/resume — same runId), but two different operations happen inside it: the tool result amends the assistant that made the call, and the resumed output adds a new message. So the node's projection ends up holding several messages.

What happens, in order — one node throughout

Assistant streamsai-run-start · pipe #1
Agent mints codecMessageId_A (crypto.randomUUID()), streams text + a tool-call part, then stops for the client.
Run suspendsai-run-suspend
RunNode state → SUSPENDED, but stays live so a resume under the same runId continues it. No new node.
Client runs the tool, submits the resultcontinuation
A run-bearing wire (routes by runId to the same node), targeting codecMessageId_A via createToolResult(A, …). It amends message A's tool part — not a new message.
Run resumes, streams the answerai-run-resume · pipe #2
A fresh invocation → a fresh pipe() → new codecMessageId_B → a second assistant message, in the same node.

The resulting projection

Run node · runId (one node)
message A · codecMessageId_A
text + tool-call part
↳ amended in place by the tool result (part → output-available)
message B · codecMessageId_B
the continuation — the model's final answer after seeing the tool output
Two operations, don't conflate them: the tool result amends an existing message (matched by codecMessageId + toolCallId); the resume adds a message. Both land in the one run node — so the projection is N>1.
Why OpenAI parks client-side tools — and what it is not. It is not parked because of the N>1 projection. It's parked because client-side tools aren't a first-class concept in the OpenAI Responses API the way they are in the Vercel AI SDK — Responses has no built-in "pause, hand this tool to the client, resume with its result" notion. So the real, unsolved work is designing how to model client tools on top of Responses at all (what the suspend point is, how a result re-enters the input, approvals, the run-outcome mapping). The projection going N>1 is a downstream mechanical consequence that falls out once that design exists — a small, Vercel-templated change (next section), not the blocker.
4If we ever need OpenAI N>1 — the exact change

Not something to build now — but knowing it's small is the point. It's a self-contained, codec-side edit with Vercel as a line-for-line template. Three steps:

  1. Change OpenAIProjection from a single turn to a list of turns keyed by codecMessageId (mirror VercelProjection.messages + a per-turn byItemId).
  2. In fold, route each event to the turn for meta.messageId via an ensureTurn(codecMessageId) helper — instead of writing to the one turn. (The reducer already reads meta.messageId; today it just collapses it into the scalar state.codecMessageId.)
  3. Have getMessages return one CodecMessage per distinct codecMessageId, instead of a single-element list.
No core change. No public-API break (only the internal projection shape moves). A complete reference implementation (Vercel) sits right next to it. item_id stays the intra-turn key throughout — globally unique, so it can't collide even across turns.

The one sentence to hold onto

Tree → Node → Projection → Message(s) → items: nodes segregate replies (by runId) and inputs (by codecMessageId); a projection holds one message (OpenAI) or many (Vercel) keyed by codecMessageId; items are identified by globally-unique item_id, never by position — and moving OpenAI from one-message to many is a localised, non-breaking codec change with Vercel as the template.
