decodeLifecycle — the contract, the hooks, the lifetimes

What decodeLifecycle is, what its two hooks (onDiscrete and onStreamStart) mean, and — the part that's easy to get wrong — how long the state they hold lives and how often it's created. Grounded in the OpenAI codec, but the contract is generic (core owns it; Vercel and OpenAI both implement it).

1 · The one-sentence purpose

A decoder turns Ably wire messages into codec events, which a reducer folds into the rendered conversation. The reducer's contract (documented on Reducer in src/core/codec/types.ts) is strict: it is handed each event exactly once, in canonical order, and it must not dedupe or skip — "ordering, deduplication and replay are the transport's responsibility, not the reducer's."

That works only if the event stream the reducer receives is well-formed — every event that later events depend on actually arrives, and nothing arrives twice. decodeLifecycle is the small policy that keeps the stream well-formed when a client joins mid-flight (a second tab, a reconnect, a history-page boundary): it reconstructs the lead-in events the joiner missed, without ever injecting a duplicate. It is the decoder's job — so the reducer stays dumb.

2 · The shape: a policy is two hooks

decodeLifecycle in defineCodec is a factory that returns a LifecyclePolicy — an object with (optionally) two hooks: 

decodeLifecycle: () => ({
  onDiscrete: { <codecKind>: (runId, ctx) => TOutput[] },   // keyed by the wire "kind"
  onStreamStart: (runId, tracker) => TOutput[],
})

Both hooks do the same two things: perform a side effect on the policy's own state, and return lead-in events to prepend. The generic decoder always runs the real descriptor decode afterwards and appends its output — so a hook can only add events in front of a decode, never replace it (see LifecyclePolicy's JSDoc in src/core/codec/define-codec.ts).

onStreamStart

Fires when the decoder first meets a streamed ai-output message — the once-per-stream "start". That's both a genuine live start and a mid-stream join (the platform hands a late subscriber the in-flight streamed message as one full-contents update, which is still a "start" to a fresh decoder).

Gets (runId, tracker). The tracker holds the stream's current codecHeaders (re-stamped on every append) and accumulated text. In OpenAI we read the owner item_id / part type off those headers to synthesise the missing output_item.added envelope.

onDiscrete

A map keyed by the wire kind header. When a discrete (non-streamed) ai-output message decodes and its kind matches a key, that entry fires. In OpenAI we register response.output_item.added (to notice the real envelope) and the terminal response events (to free state).

Gets (runId, ctx) where ctx carries the inbound codecHeaders and the pre-decode data. Ours returns no lead-in ([]) — it's used purely for its side effect: recording which owner items it has seen.

Why the wire kind is the key: every codec event carries a kind header that the decoder dispatches on (a discrete event's type, or a stream family's id). onDiscrete is looked up by that same key — and safely, via Object.hasOwn, so a hostile wire kind like "toString" can't reach through the prototype chain.

3 · What the OpenAI policy actually does

A streamed reply is several separate Ably messages: a discrete output_item.added that creates the item, then a separate streamed message (content_part.added → deltas → *.done) that fills it. Every fill event looks the item up by item_id and silently does nothing if it's missing. A joiner who missed the discrete envelope would drop the whole reply.

onStreamStart(runId, tracker) itemId = fItemId.read(tracker.codecHeaders) if no itemId -> [] # function_call_arguments: id nests in the item, no owner to add if seen(runId, itemId) -> [] # already introduced (real OR a sibling stream's synth) — no duplicate owner = message | reasoning item, chosen from the part type mark seen(runId, itemId) return [output_item.added(owner)] # prepended; buildStart's content_part.added + deltas follow onDiscrete["response.output_item.added"](runId, ctx) seen(runId, itemId-from-ctx.data).add() ; return [] # the REAL envelope arrived — record it onDiscrete["response.completed" | ".incomplete" | ".failed"](runId) forget everything for runId ; return [] # run over — free the per-run set

The seen set is the whole trick: synthesise the envelope only when it's genuinely absent, so a client that did see the real one (present at the start, or a full history replay) never gets a second copy. That's what keeps the reducer's "exactly once" promise intact.

4 · Lifetimes — the part you asked about

The factory closes over a Map<runId, Set<itemId>> (the seen state). So the obvious worry is right to ask: how often is that Map created, and how long does it live?

Thing Created Count Lives for
The LifecyclePolicy + its seen Map Once, inside createDecoder() — the factory is called exactly once per decoder 1 per decoder The decoder's whole life
The decoder Per materialisation, in createMaterialisation() 1 per materialisation ClientSession builds one for its whole life; AgentSession discards and rebuilds it (and its per-run seen state) on Tree reset
A seen entry (one run's Set) Lazily, first time a run's event is decoded 1 per run Until that run's terminal response.* event clears it

So: one policy per materialisation (a ClientSession's lasts the whole session), shared by every message it decodes — both the live subscription and history hydration go through the same decoder, so its seen state must be scoped per run (item ids are only unique within a response) and cleared as runs finish, or it would grow unbounded over a long-lived session. That per-run keying + terminal clearing is exactly what the policy does.

Decode-once, fold-many. The hooks run at decode time — once per wire message (decoder.decode() in applyWireMessage). The Tree stores the resulting events and re-folds them through the reducer when a late message forces a node to rebuild. Refolds replay the already-decoded events; they do not re-run the decoder or the lifecycle hooks. So the seen state is consulted once per wire message, never on a refold — the synthesised lead-in is baked into the stored event list the first time.

5 · The invariant, restated

Everything above serves one line of the reducer contract: the reducer is handed a clean, exactly-once, canonical-order stream and folds it blindly. decodeLifecycle is where the decoder earns that promise for mid-stream joiners — reconstruct what's missing, never duplicate what's present, hold only per-run state and let it go when the run ends. Approaches that instead teach the reducer to tolerate duplicates or to fabricate missing parents would move this responsibility across the layer boundary the contract draws — which is why the repair lives here.
