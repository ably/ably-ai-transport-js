Mid-stream join & decodeLifecycle

The OpenAI codec rebuilds an assistant message by folding a sequence of wire events. The order matters: the output_item.added envelope must arrive first to create the item, because every later event looks the item up by item_id in a map called byItemId — and silently does nothing if it's missing. Pick a scenario and step through to see what happens.

Why only the envelope is missing — streamed vs discrete

On the wire a run isn't one stream of events — it's a few separate Ably messages. The text is one streamed message that Ably hands any subscriber in its current accumulated state, so the decoder can always rebuild it. The envelopes are separate one-shot messages published around it; a late joiner only gets those if they're still in the rewind / history window.

When does a client actually land mid-stream?

Each of these delivers the streamed text message but can miss the earlier output_item.added. Exactly how often each fires depends on Ably's rewind / history window — confirming which ones really reproduce is the first task before building the repair.

Second tab / device, mid-reply

live join
You open the chat in another tab — or another participant joins — while the assistant is still typing, attaching after the envelope was already published.

Reconnect after a blip

resume
A client drops mid-stream and re-attaches; the resume window covers the in-flight streamed message but not the earlier discrete envelope.

History pagination boundary

hydrate
Loading history a page at a time, the page boundary falls between the envelope and the streamed message — so a page has the text without its envelope.

Retention / compaction

long-lived
Over time the channel expires or compacts the one-shot envelope message while the streamed message persists.

Not this: a normal refresh that replays full history including the envelope rebuilds fine — which is why the demo's refresh / history test already passes. The gap is specifically joining where the envelope is out of reach.

Is fabricating the output_item.added honest?

The synthesised item is a real ResponseOutputMessage. Every required field is set to something true for "a streamed assistant text message, mid-flight" — no cast needed, nothing left undefined. And the reducer only ever reads type and content, so reconstruction doesn't even depend on the rest.

FieldWe setHonest?
idthe real item_id (the stream's id)✓ real value
type"message"✓ fixed literal — the text stream only ever wraps a message item
role"assistant"✓ fixed literal — output messages are always assistant
status"in_progress"✓ true while streaming; the reducer ignores it, and a later output_item.done upgrades it to "completed"
content[]✓ filled by the real deltas as they fold in
phase?omitted⚠ the one lossy bit — optional, and absent for our text models (gpt-4.1). Newer models (gpt-5.x) may set it, and OpenAI warns that dropping it on resend can degrade follow-ups. Self-heals if the real output_item.done arrives.
Self-healing: the fabrication is a placeholder. The moment the authoritative response.output_item.done folds in, it replaces the synthesised item wholesale (carrying the real status and any phase). The fabricated values only persist when reconstructing a history slice that has the deltas but neither envelope — and even then the visible text is correct; only status / phase are approximate.

The takeaway

  • Scenario 1 (present from the start): the output_item.added envelope arrives first, so every part & delta finds its item. Message builds fine — this is also what full history replay gives you.
  • Scenario 2 (join mid-stream, no repair): the late client's decoder reconstructs the streamed part & deltas, but the output_item.added envelope was a separate, earlier event it never saw. Every lookup MISSES → the message silently never renders.
  • Scenario 3 (join mid-stream, decodeLifecycle): the decoder's onStreamStart hook synthesises the one missing output_item.added and prepends it. Now the item exists before everything else → it all lands.
  • Why only the envelope? The content_part.added is the stream's declared start, so the decoder's own buildStart already rebuilds it. You only fill the gap nothing else covers: the item envelope. (Synthesising the content part too would create a duplicate empty part.)
