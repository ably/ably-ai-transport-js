The stream() codec construct — what it actually compiles to

When a codec declares a stream(...) family it isn't "marking some events as streamable" — it's wiring three of its event types onto one Ably message that grows over time. This is the foundation the streaming limitations and decodeLifecycle both hang off. Here's exactly what you're making happen.

1Two ways to put data on a channel

Everything a codec emits becomes one of these two shapes on the Ably channel:

Discrete — what event() declares

You publish a complete, immutable message. It has its own serial (Ably's unique id) and never changes.

One event → one message. Used for lifecycle, the item/part envelopes, the tool result — anything that isn't incremental text.

Streamed — what stream() declares

You publish one message, then append fragments to that same message over time. Ably natively supports mutating a published message (append/update, keyed by its serial).

The message grows in place; subscribers watch it get longer. Used for the one thing that's genuinely incremental: streamed assistant text.

stream() in one sentence: "these three event types of mine — a start, a delta, an end — are not three messages; they're the birth, growth, and death of a single growing message."
2What you declare when you call it

You hand it three of your codec's event types and tell it which fields carry the identity and the growing text:

stream('text', {                              // the family id — the wire "kind"
  start: 'response.content_part.added',       // the birth event
  delta: 'response.output_text.delta',        // a growth increment
  end:   'response.output_text.done',         // the death event
  idField:    'item_id',     // which field names *this* stream
  deltaField: 'delta',       // which field holds the growth increment
  fields: [fOutputIndex, fContentIndex, fPart],  // extra props to carry on start/end
})
start / delta / end — three distinct event types. Their only structural job is to mark the three phases of one stream.
idField — the property whose value is the stream's identity. It becomes the Ably message's handle (and the stream-id header). Must be one top-level string, present on all three phases.
deltaField — the property on the delta event holding the text fragment to append.
fields — any other properties to auto-carry as headers on the start/end (e.g. output_index, content_index, part). See §5 for how they serialise.
3Encode: the three ops it compiles to

At encode time (encoder.ts) each phase becomes one channel operation. Watch the single message S grow:

your event
channel operation → message S
content_part.added item_id=m1
startStream → publish S · data:"" · status:streaming · stream-id:m1
output_text.delta "Hel"
appendStream → append "Hel" · S = "Hel"
output_text.delta "lo wor"
appendStream → append "lo wor" · S = "Hello wor"
output_text.delta "ld"
appendStream → append "ld" · S = "Hello world"
output_text.done
closeStream → append · status:complete · flush
  • startStream(streamId, …) publishes one message and Ably returns its serial — the permanent handle. The encoder remembers streamId → serial and starts an accumulated string. The fields are stamped as codec headers here.
  • appendStream(streamId, fragment) appends to that serial (appendMessage({ serial, data: fragment })), adding to accumulated. Fire-and-forget (batched, flushed on close). Every append re-stamps the start's headers — Ably replaces the whole extras object per append, so they'd vanish otherwise.
  • closeStream(streamId, …) appends a final fragment flipping status:complete, then awaits all pending appends.
The result on the channel is one message that grew from "" to "Hello world" — carrying a status header that walked streaming → complete. Not five messages: one.
4Decode: the exact mirror image

The DecoderCore (decoder.ts) is stream() run backwards: it maps Ably message actions back into your codec's events, via the descriptor's build hooks. An append literally becomes a delta:

inbound Ably actiondecoder hookyour event
message.create (streamed)buildStartcontent_part.added
message.appendbuildDelta(tracker, fragment)output_text.delta
message.append · status:completebuildEndoutput_text.done
message.create (not streamed)decodeDiscreteoutput_item.added, …

The append's own data is the fragment: buildDelta emits { item_id: streamId, delta: fragment } straight to the reducer. So the reducer replays the same start → delta* → end shape it would have seen live.

Automatic rebuild vs. the decodeEnd override — why some hooks are default and some are custom. Each build step is automatic by default: reconstruct the chunk from the declared fields + the stream id (+ the fragment, for a delta). That suffices whenever a chunk is fully described by its headers — which start and delta always are (start has no text yet; a delta is the fragment). The end is the exception: output_text.done must carry the full accumulated text, which lives in the stream tracker (accumulated), not in any header — so the field-rebuild can't produce it. That's why the codec supplies decodeEnd: an escape hatch handed { streamId, accumulated, closingHeaders } to build the real end chunk. buildEnd is just the driver step — "use decodeEnd if the codec gave one, else do the automatic rebuild." The rule everywhere: automatic from headers; a hook only where the headers can't express the chunk (the end's accumulated text; or decodeDiscrete, for when a streamed family arrives as a plain message via history compaction).
The load-bearing guarantee of the entire codec — internalise this one. However a client arrives at a run — subscribed from the very first token, opening a second tab mid-reply, reconnecting after a dropped connection, or hydrating the whole conversation from history long after it finished — the reducer is handed the same coherent stream of events, semantically equivalent to what the agent originally emitted. Where the wire physically cannot reproduce an event (a discrete envelope a late joiner never received), the codec synthesises it (decodeLifecycle) so the sequence stays whole. The reducer therefore never branches on "how did I get here?" — there is no live-path vs history-path vs mid-join-path logic in it. It folds one contract, and every possible arrival route is engineered — by the encode/decode inversion, by the stream tracker, by synthesis — to deliver exactly that contract. That is the whole reason the two-layer split exists.
But it's a reconstruction, not a byte-replay — three ways it differs, each of which explains a real bit of the codec:
  • Lossy fields. Only declared fields survive; a rebuilt output_text.done has sequence_number: 0, and deltas carry no output_index/content_index. → why the reducer keys on the stable item_id.
  • Re-chunking. A late joiner / history read gets the message as its accumulated value in one update, which the decoder expands into start + one big delta + end. The reducer folds to the same item whether it saw 50 fragments or 1. → why mid-stream join "just works" for text.
  • Missing discretes. The output_item.added envelope is a separate message a late joiner may miss. → why decodeLifecycle synthesises it.
5How fields actually get onto the wire

You don't hand-stamp output_index etc. — you declare them, and the driver reads them off the chunk automatically. A HeaderField's key does double duty: it's both the wire header name and the chunk property it reads. 

// fields.ts — one binding fixes the header key AND the property name
const fOutputIndex = jsonField<number, 'output_index'>('output_index');

// field-bag.ts — encode: read chunk[key], write header[key]
for (const field of fields) field.write(rec, chunk[field.key]);   // writeFields
// decode is the inverse: read header[key], JSON.parse, put back on the chunk (readFields)
  • The fields are read off the start chunk at startStream (and the end chunk at closeStream) — not off each delta. So their values are the start's, frozen.
  • Because appends re-stamp the start headers, those frozen values ride on every append — so output_index, content_index, and part are physically present on every fragment. (part is a snapshot: its type is real, but its text stays "" — the growing text lives in the message data, not the header.)
  • Yet buildDelta ignores them — it only rebuilds { idField, deltaField }. The fields feed buildStart/buildEnd only. So the info is on the wire; the stream() decode path just doesn't wire it into deltas. (That's where the limitations live — not in the wire.)
6The constraint that falls straight out of this

Everything hangs on one thing: a stream is one Ably message, identified by one serial, keyed by one idField string. And a decoded delta is nothing but (streamId, fragment). So a stream's identity must be:

  • one string — no composites (one message = one id);
  • present on the start event — to open the message and stamp stream-id;
  • recoverable on every delta — so each fragment routes to the right message;
  • unique — so concurrent/repeated streams don't collide on one serial.
Every streaming limitation is the same failure of that one requirement — the real identity isn't expressible as a single top-level string:
  • function-call args — the id is nested (item.id) on the only possible start event;
  • reasoning summaries — item_id isn't unique (many summary parts per item → needs + summary_index);
  • multiple text parts in one message — item_id again isn't unique (needs + content_index).
The single-part text case works only because item_id alone happens to suffice. See the companion doc streaming-fncall-args-and-reasoning.html for the full treatment.

The whole thing in three lines

Encode: stream() turns a start/delta/end trio into publish-once → append-the-deltas → close — one Ably message that grows, threaded by idField.

Decode: the DecoderCore runs it backwards — create/append/append-complete become start/delta/end events — so the reducer folds the same event contract on both sides of the wire.

Consequence: because it's one message keyed by one string, a stream's identity must be a single top-level id present on start and every delta — and that single requirement is the root of every streaming limitation.
