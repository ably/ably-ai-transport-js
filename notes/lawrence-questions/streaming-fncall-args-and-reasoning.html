Why the codec can stream text but not function-call arguments or reasoning summaries

The codec's stream(...) construct maps a provider's start → delta → done event trio onto one Ably streamed message. Everything hinges on one requirement: the codec must be able to name the stream with a single string that appears the same way on all three events. Text satisfies it; function-call arguments and reasoning summaries don't — but for different reasons, and the fields that block them tell you what a fix would need.

Lawrence's question

"All the commentary so far is based on *_id fields — but the events also carry various *_index properties (output_index, content_index, summary_index). Would those be useful, or offer an alternative approach?"

Short answer: for function-call arguments, yes — output_index is a single top-level field present identically on all three phases (it's the one thing the nested item.id lacks), so it genuinely reframes the blocker. For reasoning summaries, no — indices don't rescue it, because the id you need is inherently composite (item_id + summary_index) no matter which fields you reach for. Section 5 works through both.

1The wire mechanism a stream rides on

A discrete event is published as one self-contained Ably message carrying its own headers + data. A streamed family is different: it opens one Ably streamed message and appends bare text fragments to it. That streamed message is identified — on both sides — by a single string stream id.

Encode (agent) — output-descriptor-encoder.ts

startStream(streamId, { data: '', headers }) streamId = chunk[idField] — one string, read off the start chunk
appendStream(streamId, "frag") the delta puts only the fragment on the wire — no id, no headers, just text appended to that stream
closeStream(streamId, { headers }) the done chunk
→

Decode (client) — output-descriptor-decoder.ts

buildStart → { [idField]: streamId, …headers }
buildDelta → { [idField]: streamId, [deltaField]: "frag" } a decoded delta recovers exactly two things: the stream id and the fragment. Nothing else survives.
buildEnd → { [idField]: streamId, …closing headers }
The consequence that drives everything below: a streamed delta carries no identity of its own — Ably identifies it only by the stream id string. So the reducer can only route a fragment to the right item by that one string. Whatever names a stream must be a single string that is (a) present on the start event to open the stream, and (b) recoverable as that same string to place every fragment. This is also why the reducer keys on item_id and not OpenAI's positional output_index: the index is simply not on a decoded delta (findings §B).
2What stream(...) demands of the id

The construct's type (OutputStreamSpec in output-descriptors.ts) bakes the mechanism above into three hard constraints on idField:

single field idField names one property. There is no composite / multi-field id — the stream id is one string.
string-valued StringKeyOf<…> — the property must be string-typed. Numeric keys (all the *_index fields) are excluded by the type.
top-level A key of the chunk itself, read via chunk[idField]. A value nested under item.id is unreachable.
on all 3 phases The type is the intersection StringKeyOf<Start> & StringKeyOf<Delta> & StringKeyOf<End> — the id key must exist, string-typed, on each of the three distinct event types.
uniquely (Implied by the mechanism.) The id must uniquely name one logical stream, so concurrent/repeated streams don't collide on the same Ably stream id.

4The two failures have different root causes

They're lumped together as "the id isn't a single top-level string," but that hides that they break on different constraints from section 2 — which matters, because it changes what a fix must do.

Function-call args breaks: top-level + all-3-phases  2 blockers

Blocker A — the id's location. The deltas carry item_id top-level, but the only event that precedes them (so the only candidate start) is response.output_item.added — a shared envelope that carries the id nested under item.id (and it's even optional there). The three phases share no top-level string but the constant type.

Blocker B — there is no dedicated start event. output_item.added is the same envelope that introduces every item (messages, reasoning, function calls). The encoder dispatches purely on type, so it can't make that one event a stream-start for function calls yet a discrete envelope for text. This is the deeper reason the spike modelled args as discrete events, not a stream(...) family.

Reasoning summaries breaks: uniqueness  1 blocker

It clears every constraint except uniqueness. There is a dedicated start (reasoning_summary_part.added), and item_id is top-level & string on all three phases.

But item_id alone names the wrong thing. A single reasoning item streams one or more summary parts — each its own start→delta→done cycle — all sharing one item_id, separated only by the numeric summary_index. Keying the stream on item_id would collapse several parts into one garbled stream. The id you actually need is the pair:

`${item_id}:${summary_index}`

Function calls: yes, output_index is a real alternative

Look down the output_index column for fn-call: it's top-level on all three phases — including output_item.added, the exact place item_id is nested. So it satisfies findings §A's stated blocker ("no single top-level id shared by start/delta/end"). The blocker shrinks from "teach the model to read a nested key" to just "allow a numeric (or coerced) key."

Two caveats before celebrating. (1) output_index is positional and resets to 0 each /responses call; a run's agentic loop makes several, so an id of just output_index would collide across turns in one run — item_id is globally unique and doesn't. (2) It does nothing for Blocker B: the start is still the shared output_item.added envelope the encoder can't specialise by item type.

Reasoning: no, indices don't collapse it

The problem isn't a missing field — it's that the unit of streaming is below the item. item_id is present but not unique; summary_index is unique within an item but not across items. Neither alone is a stream id.

Any working id here is a pair — item_id:summary_index (or output_index:summary_index). That's still two fields, so it defeats the "single top-level string key" model however you pick the fields. Indices change which pair you'd use, not whether you need one.

So what actually unblocks this

  • One core change covers the id-identity facet of both cases: let idField be an extractor (chunk) => string instead of only a top-level string key name (spike Observation A). Then function calls use c => c.type === 'response.output_item.added' ? c.item.id : c.item_id (globally unique, sidesteps both the nesting and the numeric-key issue), and reasoning summaries use c => `${c.item_id}:${c.summary_index}` (the composite). The reducer keys on that same string.
  • output_index is the lighter-weight alternative for function calls only — no extractor needed if the type merely allowed a numeric/coercible key — but its cross-/responses reuse makes it riskier than an item.id extractor. Good to know it exists; the extractor is the more robust pick.
  • Function calls need a second thing the id fix doesn't give: a way to start a stream on the shared output_item.added envelope for function-call items only (Blocker B). That's an encoder-dispatch problem, not an id problem — likely a per-item-type predicate on the stream start, or a bespoke escape-hatch encode. this is the harder half
  • Reasoning summaries need only the extractor — dedicated start, uniform top-level fields, no shared-envelope problem. Once idField can be composite, reasoning streams with no further work. closest to shippable
