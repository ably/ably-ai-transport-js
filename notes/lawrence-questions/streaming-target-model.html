OpenAI codec streaming — the target model

Design target · API shape deliberately deferred

Where we're trying to get to with the OpenAI codec's streaming. This pins down the behaviour we want and the gaps that stand between us and it — but stops short of the concrete stream() API changes, which are the next conversation.

1The bar
We want to stream everything OpenAI can stream.

If a piece of content streams over the OpenAI wire and our codec can't stream it, that's not a content-specific shortcoming — it means the stream() model is too narrow and needs revisiting. Streaming is the realtime service's whole pitch; "carry the final value only" is not an acceptable resting state for anything OpenAI delivers incrementally.

2The unifying insight: it's all "text growing into a slot"

Lined up, every streamable family is the same shape: a text value that grows into a slot of an item, where a slot is (item, position) and is opened by some start event. Once you see that, the differences between families are just which slot and which events name it.

item ← the whole item, addressed by item_id └─ content[ i ] or summary[ i ] ← a SLOT: one position in an item array (i = content_index / summary_index) └─ "text that grows, delta by delta" ← what the stream fills function_call is the exception: no array — the slot is the item's own `arguments` field
A stream = one growing text value bound to one slot. The slot's identity is item_id plus (at most) one position index. That identity is what makes concurrent streams distinct, and it's what the reducer needs to place the text.

Family naming rule: a family's name is the stem its own .delta and .done events share (equivalently, "the thing before .delta"), with the response. prefix dropped — unique, mechanical, self-documenting. The start is deliberately not part of the name because starts get shared across families. (This renames today's 'text' → output_text.)
Family ≠ instance. A family is a static kind of stream (a reconstruction recipe, selected on decode by the wire kind header). A stream-id is one live instance of a family — one slot. One family can have many concurrent instances (two text parts = two output_text instances, distinct stream-ids). We need multiple families because the protocol has multiple distinct kinds of streamed content — each emits its own event types and lands in its own place — and the family is what restores that "what is it?" distinction the wire strips away.
Why function_call_arguments looks asymmetric to the rest. The other four families fill a part inside an item's array (content[] or summary[]), and a part has a dedicated opener — content_part.added / reasoning_summary_part.added — that names the already-created item by top-level item_id plus a position index. That's why they only need compose (item_id + index) and get a clean dedicated start.

A function_call has no sub-array of parts — its arguments is a plain string field on the item itself — so OpenAI emits no *_part.added event for it. Its stream has to start on the only earlier anchor: the item-creation event output_item.added, which carries the whole item object inline — so the id sits nested at item.id. That one fact is the root of both its oddities: the nested id forces relocate (Cap 1), and because output_item.added also births messages and reasoning items, the stream can only claim it for function_calls — a discriminated start (Cap 3), with message/reasoning ones falling through to the plain event('response.output_item.added') descriptor we keep anyway. It's not a special case bolted on — it's what you get when the streamed value is the item's own field rather than a part inside it.
4What today's model can't express — the three gaps

Today's stream() assumes: a single top-level string id, a start event type that alone names the family, and deltas stripped to (id, fragment). The target breaks all three. So three capabilities have to exist:

Capability 1 · for the transport
Derived id = a uniqueness handle

Today the stream-id is one top-level string key, looked up the same way on every phase (chunk[idField]) — so it must be a single property present on start, delta and end alike.

Want the id computed from the chunk — which lifts two different limitations, hit by different families:

compose — build the id from more than one field, because no single one is unique: item_id + content_index (text / refusal / reasoning_text), item_id + summary_index (summary). Every coordinate is top-level here; the need is to combine them.

relocate — read the id from a different place per event, because the same id moves: fn args carry it nested at item.id on the start but top-level item_id on the deltas. One coordinate; the need is where it lives.

Either way it stays an opaque uniqueness handle for the Ably message — never parsed by the reducer.

Capability 2 · for the reducer
Deltas keep their real fields

Today for each fragment the decoder builds a delta event object for the reducer, filling in { item_id, delta } — but item_id there is really just the stream id echoed back (today the stream id and item_id are the same value). It leaves out the position index, so the reducer can't tell which part the text belongs to and just appends to the last one ("the trailing part").

Want the decoder to also fill in the position index on that object, so it builds { item_id, content_index, delta } rather than { item_id, delta }. The content_index is already on the wire (re-stamped on every append) — the decoder just isn't copying it onto the object today. With it there, the reducer reads content_index straight off the event to place the text in the right slot — never by parsing Cap 1's id — and the object matches what the agent emitted (source-agnostic).

{ type: "response.output_text.delta", item_id: "msg_1", content_index: 0, ← today omits this delta: "Hel" }
Capability 3 · for dispatch
Start type alone can't name the family

Today the encoder picks a family by the start chunk's type alone. That breaks the moment a type is shared: content_part.added opens text or refusal or reasoning_text (told apart by part.type); output_item.added opens the fn-args stream only when item.type = function_call.

Want one policy: a stream starts on the event that first reveals its slot. That reveal is sometimes a shared event, so the encoder resolves the start by a payload discriminator (part.type / item.type), not just type. When it names no stream, the stream doesn't claim the event — the explicit event('response.output_item.added') descriptor (kept anyway) handles it. stream() never publishes a discrete message itself.

(For a function_call the reveal is output_item.added — the slot is the item's own arguments, born with the item; for content/summary it comes one event later, at *_part.added. See §3. A broader core alternative — a stream with no start event, opened lazily on its first delta — would drop discrimination entirely, but this policy doesn't need it: every family has a reveal event, and it's the richer start since it carries the slot's part/item + index.)

Caps 1 and 2 look redundant but aren't — in fact Cap 1 forces Cap 2. Today the decoded delta's item_id is just the stream id echoed back (same value). The moment Cap 1 makes the stream id composite (msg_1:0), it can't be echoed as item_id — that would corrupt it and the reducer's byItemId lookup would miss — so item_id must instead be reconstructed from a real re-stamped field, and the composite id stays a transport-only handle the reducer never sees. Cap 1 packs the coordinates into the id for the transport; Cap 2 reads the real coordinates back for the reducer, from the fields that ride every append — never by decoding the id.
And Cap 2 rebuilds the delta's own field set — not a blind copy of the start's. content_index belongs on a delta; part (a content_part.added field) does not — the real output_text.delta never carries it, so copying every start field across would fabricate one the agent never sent (breaking source-agnosticism). So "fields on the delta" means the fields that delta type actually has — a per-phase set — whose values happen to be available from the re-stamped start headers.

5Where the text lands — the reducer side

Streaming isn't done when the text is on the wire — it has to fold into the right place in the projection. With Cap 2 (fields on deltas), the reducer routes each delta by real coordinates:

  • output_text / refusal / reasoning_text → the part at content[content_index] of the addressed item (append text / set refusal).
  • reasoning_summary_text → the summary part at summary[summary_index] of the reasoning item.
  • function_call_arguments → the arguments string of the function_call item (item-level, no sub-index).
The derived stream-id (Cap 1) is used only as the transport's uniqueness handle for the Ably message — never parsed by the reducer. The reducer routes purely on the real fields carried on each chunk (Cap 2). Clean separation: id = transport handle, fields = semantic routing.
6Scope — and the one edge we're watching

The three capabilities aren't OpenAI-text-specific; they're what "stream everything" requires in general.

  • Hosted-tool streams generalise for free. mcp_call_arguments.delta, code_interpreter_call_code.delta, custom-tool input, etc. are all "text/data growing into an item's slot, opened by a discriminated item envelope." If the three capabilities land, these are just more descriptor entries — which is the evidence the model is sound, not broken.
  • The one edge: binary modalities. Audio bytes and partial images aren't text deltas. They either ride as base64 strings (fits, since deltaField is a string) or need a binary delta payload — a genuinely separate consideration we're consciously setting aside for now, not pretending it fits.

What this doc deliberately doesn't decide

The API shape. How a family declares a derived id, how a delta opts into the field-rebuild, and how a shared start declares its discriminator (with the discrete fallback) — those are concrete stream() / descriptor surface changes, and they're the next conversation. This doc is the destination we're designing toward; the surface is how we get there.
