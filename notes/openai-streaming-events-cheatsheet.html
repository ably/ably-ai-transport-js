OpenAI Responses streaming — event cheat sheet

⚠️ Out of date. Written for an earlier shape of the OpenAI codec; not refreshed for its current wire model (drop-based wire curation, slimmed output_item.done, payload-less terminal lifecycle events, and the deltaFields → decodeDeltaFields rename). Background only — do not rely on the specifics.

A single /responses call streams dozens of small events: a log of edits. No event is a self-contained record — each one creates or mutates a node in the Response object being assembled, and addresses that node with a fixed set of ids and indices. This sheet shows the shape being built, what every coordinate points at, which event touches which node, and how it all interleaves on the wire.

item id output_index content_index summary_index annotation_index call_id sequence_number
1The shape being assembled

A Response is a flat output[] array of items. An item is a message, a reasoning block, a function call, or a hosted-tool call. Only some items have inner arrays — a message has content parts; a reasoning item has summary parts (and optionally raw content parts). The badges are the coordinates that address each level.

Three levels of nesting, four index axes — one nesting rule repeated. Every level is "an array whose positions are named by an index": output_index selects the item in output[]; content_index selects a part within a message/reasoning item; summary_index selects a summary part within a reasoning item; annotation_index selects a citation within a text part. Each deeper axis just repeats the same idea one level in. The exception is function_call: it has no inner array — its arguments is a single JSON string — which is why its stream carries only item_id, no inner index at all.
2How the ids & indices link up

Every streamed event carries some subset of these. Ids name a thing; indices name a position. The two overlap on purpose — an event usually gives you both a stable id and a positional index for the same node.

item id
wire: item_id (top-level) · or item.id (inside an envelope)

The item's own stable, globally-unique id (msg_, rs_, fc_…). Names a node in output[] without caring about position.

output_index
wire: output_index (number)

The item's position in output[]. Present on nearly every event as the fast path to the item. Positional, so it resets to 0 on each new /responses call — not unique across a multi-call run.

content_index
wire: content_index (number)

Position of a part within a message's content[] (or a reasoning item's content[]). Text, refusal, annotation, and reasoning-text events carry it; function-call events don't.

summary_index
wire: summary_index (number)

Position of a summary part within a reasoning item's summary[]. The reason a reasoning item's id alone isn't a stream key: one item, many summary parts, distinguished only by this.

annotation_index
wire: annotation_index (number)

Position of a citation within a text part's annotations[]. The deepest axis — three levels down (output → content → annotations). Only output_text.annotation.added carries it.

call_id
wire: call_id (on the function_call item)

Distinct from the item id. Pairs a function_call with its function_call_output — the value that ties a call to its result across turns.

sequence_number
raw event only: sequence_number (number)

A single monotonic counter OpenAI stamps on every raw event — the raw stream's ordering. Listed here because you'll see it on every raw event; it addresses nothing in the Response's structure.

3The event catalogue — which node of the Response each event builds

Grouped by tier: whole-response lifecycle, the item envelope, the content-part envelope, then the streaming families that fill parts. For each event, the catalogue lists the identifying coordinates it carries and what it means in OpenAI's protocol — what the event actually carries (its payload) and its role: the .added/.done envelope events carry the real item/part object (event.item / event.part), while the delta/done text events carry only a string; nothing is synthesised from an implicit rule.

Reading the coordinates column: these are the literal fields on the event object. A plain name (output_index, item_id) is a top-level property. A dotted name (item.id, underlined) is nested: the event carries the whole item object and the id sits inside it, at event.item.id — not a top-level event.item_id. Colours match the shape/legend throughout.

Why reasoning reuses some of a message's events but not others — it's array shape, not item type. The rule across the whole protocol: each array-of-parts inside an item is opened by its own "part.added" event carrying a within-array index, then filled by "text" deltas. A reasoning item just happens to have two such arrays; a message has one.
• Both messages and reasoning items have a content[] array — so both reuse content_part.added/.done (indexed by content_index). Only the fill differs by part type: output_text.* for a message's text, reasoning_text.* for reasoning content. That's the "they both happen to have content" reuse.
• Only reasoning items also have a summary[] array — messages don't — so it gets its own parallel family, event-for-event:
reasoning_summary_part.added/.done  ≡  content_part.added/.done
reasoning_summary_text.delta/.done  ≡  output_text.delta/.done
summary_index  ≡  content_index
Nothing here is reasoning-specific except the existence of the extra array — the summary family is just the content family again, pointed at a different array.

The pattern to internalise: every "content" event = item_id (which item) + output_index (its position) + an inner index that says where inside the item — content_index for message/reasoning text, summary_index for reasoning summaries, and nothing for function-call arguments (the item has no inner array). The .added/.done envelopes bracket a node; the .deltas fill it; output_item.done is always the authoritative whole-value backstop.

Two things the timeline makes concrete. (1) output_index restarts at 0 in the second /responses call — so it isn't unique across a multi-call run; the stable item id is. (2) The tool's result is not an OpenAI stream event at all — the caller runs the tool and supplies a function_call_output item (paired to the call by call_id, not item id) as input to the next /responses call.
