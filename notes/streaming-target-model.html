OpenAI codec streaming — the target model

Design target · implemented by this PR
⚠️ Out of date. Written for an earlier shape of the OpenAI codec; not refreshed for its current wire model (drop-based wire curation, slimmed output_item.done, payload-less terminal lifecycle events, and the deltaFields → decodeDeltaFields rename). Background only — do not rely on the specifics.

How the OpenAI codec treats OpenAI's streamed events, and the codec-API surface that treatment runs on. This pins down the target behaviour, the three capabilities that behaviour needed from the stream() construct, and what the PR adds to provide them — streamId, deltaFields + decodeDelta, and startWhen. Everything described here ships on this branch.

1The bar
We stream everything OpenAI can stream.

If a piece of content streams over the OpenAI wire and our codec can't stream it, that's not a content-specific shortcoming — it means the stream() model is too narrow and needs revisiting. Streaming is the realtime service's whole pitch; "carry the final value only" is not an acceptable resting state for anything OpenAI delivers incrementally.

And the bar is met with no middle ground: every event OpenAI streams outside the opt-in hosted-tool / modality surfaces is modelled — as a stream, a discrete boundary, or lifecycle — and any undescribed event throws at the encoder rather than being silently dropped (see the inventory at the tail of src/openai/codec/descriptors.ts).

2The unifying insight: it's all "text growing into a slot"

Lined up, every streamable family is the same shape: a text value that grows into a slot of an item, where a slot is (item, position) and is opened by some start event. Once you see that, the differences between families are just which slot and which events name it.

item ← the whole item, addressed by item_id └─ content[ i ] or summary[ i ] ← a SLOT: one position in an item array (i = content_index / summary_index) └─ "text that grows, delta by delta" ← what the stream fills function_call is the exception: no array — the slot is the item's own `arguments` field
A stream = one growing text value bound to one slot. The slot's identity is item_id plus (at most) one position index. That identity is what makes concurrent streams distinct, and it's what the reducer needs to place the text.

Family naming rule: a family's name is the stem its own .delta and .done events share (equivalently, "the thing before .delta"), with the response. prefix dropped — unique, mechanical, self-documenting. The start is deliberately not part of the name because starts get shared across families.
Family ≠ instance. A family is a static kind of stream (a reconstruction recipe, selected on decode by the wire kind header). A stream-id is one live instance of a family — one slot. One family can have many concurrent instances (two text parts = two output_text instances, distinct stream-ids). We need multiple families because the protocol has multiple distinct kinds of streamed content — each emits its own event types and lands in its own place — and the family is what restores that "what is it?" distinction the wire strips away.
Why function_call_arguments looks asymmetric to the rest. The other four families fill a part inside an item's array (content[] or summary[]), and a part has a dedicated opener — content_part.added / reasoning_summary_part.added — that names the already-created item by top-level item_id plus a position index. That's why they only need compose (item_id + index) and get a clean dedicated start.

A function_call has no sub-array of parts — its arguments is a plain string field on the item itself — so OpenAI emits no *_part.added event for it. Its stream has to start on the only earlier anchor: the item-creation event output_item.added, which carries the whole item object inline — so the id sits nested at item.id. That one fact is the root of both its oddities: the nested id forces relocate (Cap 1), and because output_item.added also births messages and reasoning items, the stream can only claim it for function_calls — a discriminated start (Cap 3), with message/reasoning ones falling through to the plain event('response.output_item.added') descriptor we keep anyway. It's not a special case bolted on — it's what you get when the streamed value is the item's own field rather than a part inside it. On decode, buildStart re-emits the output_item.added start from the carried item, and the family's decodeDelta / decodeEnd reconstruct item_id / name from the item envelope riding the start header.
4The three codec-API capabilities the PR adds

The previous stream() assumed: a single top-level string id, a start event type that alone names the family, and deltas stripped to (id, fragment). The target breaks all three, so the PR adds three capabilities to the descriptor surface (src/core/codec/output-descriptors.ts):

Capability 1 · for the transport
Derived id = a uniqueness handle

The limitation The stream-id was a single idField — one top-level string key, looked up the same way on every phase (chunk[idField]) — so it had to be a single property present on start, delta and end alike. No slot identity beyond "one flat id" was expressible.

What the PR adds The spec's streamId: { field } | ((chunk) => string) — a declared field, or an extractor the encoder resolves per chunk. That lifts two different limitations, used by different families:

compose — build the id from more than one field, because no single one is unique: output_text / refusal / reasoning_text compose item_id + ':' + content_index; reasoning_summary_text composes item_id + ':summary:' + summary_index — namespaced because a reasoning item's summary[] and content[] both 0-index off one item_id.

relocate — read the id from a different place per event, because the same id moves: function_call_arguments reads it nested at item.id on the start but top-level item_id on the deltas. One coordinate; what varies is where it lives.

Either way it stays an opaque uniqueness handle for the Ably message — never parsed by the reducer.

Capability 2 · for the reducer
Deltas carry their real fields

The limitation For each fragment the decoder built the reducer's delta object as { item_id, delta } — but item_id there was just the stream id echoed back (the two were the same value), and the position index was left out. A reducer therefore had no way to tell which slot a fragment belonged to — a message with more than one text part could not be filled correctly.

What the PR adds deltaFields declares the header fields a delta chunk carries — its own field set, distinct from the start/end fields. Their values are stream-invariant coordinates (item_id, content_index) re-stamped on every append, so the decoder rebuilds each delta from them; decodeDelta is the escape hatch for a field that can't be read straight from a header key (fn-args rebuilds item_id from the carried item envelope). The decoder never echoes the stream id onto the chunk — the reducer routes on real coordinates, and the transport stream id stays opaque.

{ type: "response.output_text.delta", item_id: "msg_1", content_index: 0, ← carried via deltaFields delta: "Hel" }
Capability 3 · for dispatch
Start type alone can't name the family

The limitation The encoder picked a family by the start chunk's type alone. That broke the moment a type was shared: content_part.added opens text or refusal or reasoning_text (told apart by part.type); output_item.added opens the fn-args stream only when item.type = function_call.

What the PR adds startWhen?: (chunk) => boolean on the stream spec, implementing one policy: a stream starts on the event that first reveals its slot. Several families may share a start type; the encoder starts the first family whose startWhen matches. A shared-start chunk matching no family's startWhen is not a stream start — it falls through to the discrete event() descriptor for that type (stream() publishes nothing). defineCodec's table validation permits the share: a start may double as an event() decline target; its only illegal overlap is being another family's delta/end phase.

(For a function_call the reveal is output_item.added — the slot is the item's own arguments, born with the item; for content/summary it comes one event later, at *_part.added. See §3. A broader core alternative — a stream with no start event, opened lazily on its first delta — would drop discrimination entirely, but this policy doesn't need it: every family has a reveal event, and it's the richer start since it carries the slot's part/item + index.)

Caps 1 and 2 look redundant but aren't — in fact Cap 1 forces Cap 2. Under the old model the decoded delta's item_id was just the stream id echoed back (same value). The moment Cap 1 makes the stream id composite (msg_1:0), it can't be echoed as item_id — that would corrupt it and the reducer's byItemId lookup would miss — so item_id is instead reconstructed from a real re-stamped field, and the composite id stays a transport-only handle the reducer never sees. Cap 1 packs the coordinates into the id for the transport; Cap 2 reads the real coordinates back for the reducer, from the fields that ride every append — never by decoding the id.
And Cap 2 rebuilds the delta's own field set — not a blind copy of the start's. content_index belongs on a delta; part (a content_part.added field) does not — the real output_text.delta never carries it, so copying every start field across would fabricate one the agent never sent (breaking source-agnosticism). That is why deltaFields is a separate declaration from fields: the fields that delta type actually has — a per-phase set — whose values happen to be available from the re-stamped start headers.

5Where the text lands — the reducer side

Streaming isn't done when the text is on the wire — it has to fold into the right place in the projection. With Cap 2 (fields on deltas), the reducer routes each delta by real coordinates:

  • output_text / refusal / reasoning_text → the part at content[content_index] of the addressed item (append text / set refusal).
  • reasoning_summary_text → the summary part at summary[summary_index] of the reasoning item.
  • function_call_arguments → the arguments string of the function_call item (item-level, no sub-index).
The derived stream-id (Cap 1) is used only as the transport's uniqueness handle for the Ably message — never parsed by the reducer. The reducer routes purely on the real fields carried on each chunk (Cap 2). Clean separation: id = transport handle, fields = semantic routing.
6Scope — and the one edge we're watching

The three capabilities aren't OpenAI-text-specific; they're what "stream everything" requires in general.

  • Hosted-tool streams generalise for free. mcp_call_arguments.delta, code_interpreter_call_code.delta, custom-tool input, etc. are all "text/data growing into an item's slot, opened by a discriminated item envelope." With the three capabilities in place, these are just more descriptor entries — which is the evidence the model is sound, not broken. Adding them is the follow-up ticket AIT-1121.
  • The one edge: binary modalities. Audio bytes and partial images aren't text deltas. They either ride as base64 strings (fits, since deltaField is a string) or need a binary delta payload — a genuinely separate consideration, set aside to the hosted-tools follow-up (AIT-1121) rather than pretended to fit.

The API shape, as shipped

The surface this doc once left open is now decided and in the PR: a family declares a derived id via streamId (a { field } or an extractor function), a delta declares its own field set via deltaFields (with decodeDelta as the escape hatch), and a shared start declares its discriminator via startWhen (with the discrete event() fall-through). The PR's codec-API groundwork commits introduce these one capability per commit, ahead of the family commits that use them. The authoritative surface is OutputStreamSpec in src/core/codec/output-descriptors.ts.
