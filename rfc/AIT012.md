> **Types-only API implementation:** see [ably/ably-ai-transport-js#66](https://github.com/ably/ably-ai-transport-js/pull/66) for a draft of the API surface expressed as types, intended to let us refine the design before committing to an implementation.

This RFC proposes a redesign of the AIT SDK's core abstractions around a first-class session primitive: a durable, shared record of a conversation that clients and agents read from and write to. Today the session's responsibilities are split across the client transport, the channel, and HTTP request bodies — a design that works for single-streamed responses but breaks down for agentic workflows with multi-step execution, HITL pauses, crash retries, and live control. The proposal introduces session, run, and step as explicit abstractions so behaviour stays consistent across long-lived servers, serverless runtimes, and durable-execution frameworks.

# Context

## Durable sessions

A durable session is a persistent, shared layer that decouples agents from clients. Every participant (clients, agents) sees the same view of the conversation: messages, in-progress streams, tool calls, aborts, approvals. Participants come and go freely. A client reconnects, an agent crashes and reruns, a new device attaches hours later. The session outlives all of them, and anyone attached sees the full state plus whatever's happening live.

A session can carry concurrent activity: multiple agents, multiple response streams in flight, multiple clients contributing at once. The session layer keeps everything in one ordered record.

The session layer makes the following possible:

- **Live control.** Any client can abort a running generation, steer an agent mid-response, or send a follow-up before the current response finishes, from any device. These signals flow through the session, and any agent that should react to them sees them, regardless of which client sent them or which agent started the work.
- **Multi-device continuity.** The session follows the user, not the connection. Open a second tab, switch to a phone, come back hours later, and every surface hydrates the same session and sees the same state.
- **Resilient streaming.** A client that disconnects mid-stream reconnects, rehydrates, and resumes from exactly where it left off without explicit management on the server side.

Because the session holds everything an agent needs (the user's message, the conversation so far, tool results, approvals, abort signals), an agent reads its context from the session rather than from the request that invoked it. Any process that can read the session can fulfil a run, and sharing that view is what keeps behaviour correct as agents crash and recover in serverless, durable-execution, and long-lived runtimes.

### Session vs channel

The channel is a flat, ordered log of events: the live delivery mechanism and, when persistence is configured, a source from which the session can be hydrated. Events are granular. A streamable unit within a domain message (reasoning, text output, a tool-call input) is encoded as its own channel message, opened when the unit starts, appended to as content arrives, and closed when the unit completes. A single domain message with reasoning, text, and tool-call parts therefore produces several channel messages.

The session is the structured, navigable conversation, held in the application's domain model: messages in the same shape a model API or agent framework produces, each with an id, a role, and parts (text, tool calls, tool results, reasoning, files) that may still be accumulating. The session also captures how messages and groups of messages relate to each other: parent-child relationships, branching, and which messages are part of the same piece of agent work.

The codec translates between the two. Encoding maps domain events onto channel operations: opening, appending to, and closing a channel message for a streamable unit, or publishing once for a discrete event. Decoding reverses it. Multiple channel messages combine into the parts of a single domain message, and those messages form the conversation the application reads.

Live activity always flows through the channel. Every message, every stream append, every lifecycle event passes through it, and the session is updated from that live feed. The channel is also what makes streaming resumable and resilient to connection drops.

Historical state is more flexible. The session can be hydrated from channel history, from an external store the developer owns, or from a durable-execution framework's state. The channel may carry the whole lifetime of a conversation, or only the last few minutes with history living elsewhere. Either way, the application works against the session.

In the future, a session might be composed from multiple channels (e.g. for access-controlled sub-streams of activity), and hold context beyond the message stream (e.g. shared LiveObjects state, presence information).

# Problem

## Where the current SDK falls short

The current AIT SDK doesn't yet fully deliver on this vision. It has no session primitive distinct from the transport (how a participant interacts with the conversation) and the channel (the oplog beneath). The session's responsibilities are split across the client transport, the channel, and the HTTP request body. Specific failures follow:

- **Conversation history travels on every HTTP request.** The conversation history is serialised into each request. Payloads grow with conversation length, and two clients POSTing concurrently send different views of the same conversation, so the agent's memory ends up with split-brain contexts.

- **The user's message is published by the server, not the client.** Today the user's input rides the HTTP request body and the server re-publishes it on the client's behalf. A retried client invocation would double-publish the same input and have the agent partially respond to it twice. Per-connection usage attribution conflates user and agent traffic.

- **Hydration is available only to the client, and only from the channel.** The client transport can hydrate from channel history. The server transport has no equivalent path and relies on whatever the HTTP request carries. Neither side can hydrate from an external store.

- **Retrying an agent produces competing outputs with no canonical winner.** A crashed agent leaves `turn-start` with no `turn-end` and phantoms in active-turn state. There is no protocol for a new agent to discover or supersede state left by a dead one (e.g. a retried durable execution step, or re-invocation from the client after agent crash).

- **Turns can't be suspended.** A turn ends when the agent's process ends (i.e. a single request-response cycle), so there's no way to pause a turn while waiting for a tool-call approval or other human-in-the-loop signal. Handling domain messages that update across multiple turns has added a lot of complexity to the SDK.

- **Durable-execution workflows fragment into disconnected turns.** Tasks are split across multiple durable-execution steps. There is no abstraction below the turn for grouping the executions that together fulfil one user intent, so when a step fails and is retried the failed attempt's output persists on the channel alongside the retry's output with no way to group it and discard it.

- **Aborts don't work when a task outlives a single continuous agent execution.** Abort delivery relies on a live channel subscription. Any task whose execution spans multiple agent runs (split across durable-execution steps, paused between request/response cycles for HITL, or resumed after a crash) has a gap in which no transport is listening, and an abort published in that gap reaches no listener.

- **No live control of a running agent.** The current design assumes the backend is a single streamed response. Barge-in is handled by cancelling the turn and sending a new request. But when the backend is an agentic loop, cancel-and-request discards all the work done so far. There is no way to inject additional context mid-loop, and no way to pause and resume.

- **Channel injection conflates the session with its transport.** The SDK takes a pre-constructed `RealtimeChannel` as input, so the developer wires the channel up themselves and the SDK never sees the `Ably.Realtime` client. Three concrete consequences: the SDK cannot attach an `ably-agent` header for usage attribution (that header is configured at Ably client construction, not on individual channels); the SDK cannot set sensible default channel modes at `channels.get()` time (for example enabling `OBJECT_SUBSCRIBE` / `OBJECT_PUBLISH` so `channel.objects` can back session state) — the developer must remember to do it themselves; and the one-channel-per-session shape is baked into the public surface, so extending a session to span multiple channels in future — for access-controlled sub-streams, or per-thread chain-of-thought — would be a breaking change.

# Solution

These problems can be addressed structurally by refining the SDK's abstractions to fully realise the durable sessions vision. The session is raised to a first-class primitive that both clients and agents read from and write to. Hydration is a codec-agnostic operation that both agent and client sides perform identically, whether the source is channel history, an external store the developer owns, or a durable-execution framework's state.

Above a single agent execution, two new abstractions complete the picture:

- A **run** is the logical unit of user intent. It is opened by the client alongside the user's input and closed by the agent when the work completes, is aborted, or fails. A run may span multiple agent executions (HITL pauses, durable-execution steps, resumption after a crash) all grouped under the same run.
- A **step** is one concrete execution attempt within a run. Step IDs are agent-generated, so retries produce distinct identifiers and the output of a non-complete step (failed, superseded, or abandoned) can be grouped and discarded without affecting the rest of the run's output.

The client publishes its own messages directly on the channel. Agent invocations become lightweight HTTP triggers carrying only pointers (run ID, channel name, target message ID). The agent reads everything else from the session. Abort becomes durable state on the session rather than a live-subscription event, so an abort published while no agent is running is picked up by the next agent to start work on that run.

This is the target end state. The rest of this document defines each abstraction in detail, followed by a migration plan. The SDK will get there in increments, each change solving a concrete problem rather than landing the whole redesign at once.

## Definitions

- **Session.** The complete, persistent state of a conversation. Its messages are held in the application's domain model, together with additional metadata that the domain model alone cannot express: how messages relate to each other (parent-child, branching, grouping by run and step) and any in-progress streaming state. It lives independently of any participant. Clients and agents come and go, but the session stays. Two participants materialising the same session from the same data arrive at the same state. The session is what clients and agents read from and write to.

- **Channel.** An Ably realtime channel: a flat, ordered log of events that acts as the session's durable oplog. It's the live delivery mechanism, and, when persistence is configured, a source from which the session can be hydrated. Channel events are granular: a streamable unit within a domain message is published as its own channel message, opened when the unit starts, appended to as content arrives, and closed when complete. It's bidirectional, so any participant may publish at any time. Today a session maps to a single channel, though a session may eventually span multiple channels.

- **Codec.** The translation layer between domain messages and channel operations. Encoding maps a stream of domain events onto channel operations: opening, appending to, and closing a channel message for each streamable unit, or publishing once for a discrete event. Decoding reverses it: multiple channel messages combine into the parts of a single domain message. An interface, not an implementation. The transport depends on the codec contract and knows nothing about the domain model.

- **Tree.** The data structure within a session that holds every node on every branch of the conversation. Materialised from transport headers on channel messages. Unfiltered: contains everything, emits events for every mutation regardless of branch. The canonical source of conversation structure within the session.

- **View.** A linear projection over the tree. Selects one sibling at each branch point and produces the flat sequence of messages a participant works with. Also the write surface: send, regenerate, edit, and update are operations on a view. Each view has independent branch selections and pagination state.

- **Message.** The atomic unit of conversation content and a node in the tree. Identified by message ID. A domain message may be discrete (a single publish) or made up of one or more streamable units, each published to the channel as a sequence of appends sharing the same message ID.

- **Run.** The logical unit of user intent. Opened by the initiating participant — a client, a backend handler on a client's behalf, or a parent agent — alongside the input message (`x-ably-run-start`), with a run ID generated by the initiator. Closed by the agent when the work completes, is aborted, or fails (`x-ably-run-end`). May span multiple agent executions (HITL pauses, durable-execution steps, resumption after a crash) all grouped under the same run. The unit of control signals (abort, pause, resume, retry), steering, and concurrency within a session.

- **Step.** One concrete execution attempt within a run. Sequential within a run, with an agent-generated unique ID. A step may end explicitly (`x-ably-step-end`) or implicitly (process crash, resolved by the abandonment rule). Messages published by the agent within a step carry that step's ID in `message.extras` as `x-ably-step-id`, so the output of a non-complete step can be grouped and discarded without affecting the rest of the run.

- **Invocation.** The lightweight HTTP request that asks an agent to handle a run. Carries a channel name, a run ID, and, optionally, a step ID and/or message ID — references to events that must be visible on the channel before the agent begins. Carries no message content and no history. The agent waits for every referenced event to arrive, then reads the rest from the session and acts based on the run's current state. Has no lifecycle or identity on the channel.

- **Client transport.** Long-lived client-side object. Subscribes to the channel, materialises the session into a tree, provides one or more views, handles client writes (publishing user messages, sending invocations, publishing control signals).

- **Agent transport.** Server-side object used by the agent to interact with the session. Hydrates the session, publishes lifecycle events, pipes the model stream through the codec encoder, listens for signals targeting the active run. Its lifetime depends on the runtime: a serverless process might create one per invocation, a durable-execution worker might create one per step, and a traditional long-lived server might keep one around and create many runs through it.

## Principles

Design invariants that every subsequent section relies on.

- **The session is a first-class layer, distinct from the transport and the channel.** The session is the durable, shared record. The transport is how a participant interacts with it (clients and agents have different transports but work with the same session). The channel is the oplog beneath. The session abstraction is what lets the SDK behave uniformly regardless of whether the channel retains full history or only live activity.

- **The channel is the oplog. The session is the materialised view.** Every event flows through the channel. The session is the result of interpreting that log according to the protocol's rules.

- **Every message is self-describing.** All metadata needed to interpret a message is on the message itself. No context from surrounding events is required.

- **Participants never condition on absence of state.** The set of messages visible to any participant is eventually consistent, so no participant can assume "I haven't seen X, therefore X doesn't exist." A participant either acts on observed state, or waits for expected state to arrive. When two participants end up performing the same activity because neither had yet seen the other's, the total order by serial arbitrates the winner.

- **Total order by serial is the sole arbiter.** No distributed consensus, no locking. Races (between duplicate agents, concurrent clients, out-of-order delivery) resolve through serial comparison.

- **Invocations are pointers, not payloads.** Content lives on the channel. The invocation tells the agent where to look.

- **Non-complete step output is identifiable.** Every agent-published message carries the step ID that produced it in `message.extras` as `x-ably-step-id`, and lifecycle events mark steps as `failed`, `aborted`, `paused`, `superseded`, or (by the absence of `x-ably-step-end`) abandoned. Any participant has enough information to identify and decide how to handle them.

- **Client-published messages belong to the run.** They belong to the run and survive any step failure. This makes user input durable independent of agent lifecycle.

- **Header namespaces are disciplined.** `x-ably-*` is transport, `x-domain-*` is codec. Neither layer reads or depends on the other's namespace.

## Wire Headers

All transport metadata travels in `message.extras.headers` under the `x-ably-*` namespace. Codec-specific metadata uses `x-domain-*` (see Principles). The complete set of transport headers used by the protocol:

### Identity

- **`x-ably-msg-id`** — unique ID for every content message. Assigned by the publisher (UUID). On a streamed message, the same ID is set on the create, every append, and the close so the whole lifecycle shares one identity. It is the primary key in the tree, the target of an invocation's `messageId` precondition, and the value referenced by `x-ably-parent` and `x-ably-fork-of`.

- **`x-ably-client-id`** — optional override of the publishing connection's `message.clientId` for attribution. Present on `x-ably-run-start` when a backend handler publishes on behalf of an end-user (server-side input validation), and present on client-published content messages and control signals when they are routed through a backend. When absent, `message.clientId` (set by Ably from the authenticated connection) is the authoritative identity. The distinction matters because the Ably connection that publishes a message is not always the participant the message should be attributed to.

- **`x-ably-role`** — `user` or `assistant`. The participant type that produced the message, regardless of the publishing connection. Client-initiated publishes (user input, HITL approvals, steering) are `user`; agent-initiated publishes (model output, tool results produced by the agent, step lifecycle messages) are `assistant`. Exposed as a transport header so materialisers, routers, and access-control layers can distinguish participant types without decoding the domain payload.

### Correlation

- **`x-ably-run-id`** — the run a message belongs to. Set on every content message, every lifecycle event (`x-ably-run-start`, `x-ably-run-suspend`, `x-ably-run-end`, `x-ably-step-start`, `x-ably-step-end`), every control signal, and every steering message. This is the only header required to scope a message to a run.

- **`x-ably-step-id`** — the step a message belongs to. Set on every agent-published content message within a step, on `x-ably-step-start` and `x-ably-step-end`, and on resume/retry control signals that target a specific prior step. Absent on client-published messages (they belong to the run, not to any step) and on `x-ably-run-start` / `x-ably-run-suspend` / `x-ably-run-end` (which bracket the run, not a step).

### Structure

- **`x-ably-parent`** — the `x-ably-msg-id` of the preceding message in the conversation branch. Establishes linear order at branch points, where serial alone is insufficient because siblings may interleave in time.

- **`x-ably-fork-of`** — the `x-ably-msg-id` of the message this one replaces. Creates a sibling group in the tree. Used by regenerate (the new assistant message forks from the prior assistant message) and edit (the new user message forks from the prior user message).

### Lifecycle status

- **`x-ably-status`** — on lifecycle events, carries the specific status:
  - `x-ably-run-suspend`: `awaiting-input` / `paused`
  - `x-ably-run-end`: `complete` / `aborted` / `failed`
  - `x-ably-step-end`: `complete` / `failed` / `aborted` / `paused` / `superseded`

### Message names

All transport-emitted messages — lifecycle events and control signals alike — use Ably message `name` fields in the `x-ably-` namespace. Lifecycle events: `x-ably-run-start`, `x-ably-run-suspend`, `x-ably-run-end`, `x-ably-step-start`, `x-ably-step-end`. Control signals: `x-ably-abort`, `x-ably-pause`, `x-ably-resume`, `x-ably-retry`. Content messages use codec-defined names — the domain payload in `data` carries the actual content. Every transport-emitted message carries `x-ably-run-id` in headers; step-scoped messages and signals additionally carry `x-ably-step-id`.

## Lifecycle Events

Lifecycle events bracket the work happening on a session. They are durable, control-plane signals published to the channel as discrete messages, telling every participant what has been asked of the system, what is executing, and when it has finished. Two abstractions structure them. A **run** is a single unit of work performed in response to a participant's intent. A **step** is one continuous stretch of agent execution within a run: the unbroken work done by a single process from when it begins acting on the run until its execution ends.

How a given application maps onto runs and steps depends on the shape of the agent and system. Some concrete examples:

- A one-shot streamed LLM response from a long-lived server: one run, one step.
- A full agent loop (model → tool → model → ...) running to completion inside a single serverless invocation: one run, one step. The whole loop is one unbroken execution.
- A run that pauses mid-way for human-in-the-loop approval and then continues: one run, two steps separated by an `x-ably-run-suspend`.
- A durable-execution workflow that persists state across scheduled stages: one run, one step per scheduled stage.
- A crashed attempt followed by a client retry: one run, two steps (the abandoned attempt plus the retry).

Every lifecycle event is observable on the channel, so any participant, including one that joins late, reconnects after a drop, or arrives after a crash, can interpret exactly what happened without consulting any process state. The specific events for each abstraction are introduced in the subsections below.

### Runs

A run is the abstraction above a single agent execution. It exists to provide:

- **A unit of abort and pause.** Stopping a task means stopping the whole task, not a specific stream or step.
- **A grouping for multi-execution work.** HITL pauses, durable-execution stages, and crash retries all produce multiple executions in service of the same intent. The run ties them together.
- **A durable intent on the channel.** A run that has been opened but not yet picked up by any agent is observable by any participant (a second device, a queue, an orchestrator, a monitoring surface).
- **The unit of concurrency within a session.** A single session can carry any number of open runs at the same time. Concurrency arises from multiple concurrent requests from a single client, concurrent requests from different clients on the same session, concurrent agents working in parallel (for example, a parent agent fanning out subagent runs), or any combination. Each source opens its own run, and the session carries them side by side.

Concretely, a run is bracketed on the channel by `x-ably-run-start` and `x-ably-run-end`. The run ID is generated by the initiator and first appears on the channel in `x-ably-run-start`. Every message produced in service of the intent (initiator input, agent output, lifecycle events) carries the run ID in `message.extras` as `x-ably-run-id`. Agent-published messages that belong to a specific step additionally carry the step ID in `message.extras` as `x-ably-step-id`.

The `x-ably-run-start` message also carries `x-ably-client-id` identifying the participant that owns the run. When a client publishes `x-ably-run-start` directly, `x-ably-client-id` is omitted and `message.clientId` (set by Ably from the authenticated connection) is the owner. When a backend publishes on behalf of a user, `x-ably-client-id` carries the end-user's clientId explicitly so attribution survives the routing hop.

Runs are typically initiated by a client in response to a user action. They can also be initiated by a backend handler acting on a client's behalf (see [Server-side input validation](#server-side-input-validation)), or by an agent (spawning a subagent, fanning out parallel work, invoking another agent). Whoever initiates the run generates its run ID.

#### Lifecycle events

Three events bracket and punctuate a run. All are discrete channel messages and carry the run ID in `message.extras` as `x-ably-run-id`.

##### `x-ably-run-start`

Opens the run. Published by the initiator — a client, a backend handler on a client's behalf, or a parent agent — alongside its input messages, carrying the run ID generated by the initiator. No reason field. Opening is unconditional.

##### `x-ably-run-suspend`

Suspends an open run without closing it. Intermediate, not terminal. Suspension is the general non-terminal halt of a run; the status names its cause. Carries `x-ably-status` in `message.extras` with one of:

- `awaiting-input`: the agent has finished a step whose output requires external input (a tool-call approval, a follow-up user message, or any other external input the codec domain defines) before the next step can begin. Published by the agent.
- `paused`: the run was paused. Published by the agent in response to an `x-ably-pause` control message (see [Control Signals](#control-signals)).

Suspension ends when a new step starts.

##### `x-ably-run-end`

Closes the run terminally. Always published by the agent. Carries `x-ably-status` in `message.extras` with one of:

- `complete`: the task finished successfully. Published once the final step produces its output.
- `aborted`: the run was aborted. Published in response to an `x-ably-abort` control message (see [Control Signals](#control-signals)).
- `failed`: the task could not be completed after exhausting recovery. Published when no further recovery is worth attempting.

#### Initiator opens, agent owns the lifecycle

The initiator publishes `x-ably-run-start` alongside its input. From that moment, the agent handling the run owns the run's lifecycle. Every subsequent lifecycle event (`x-ably-run-suspend`, `x-ably-run-end`) is published by the agent, at a point the agent chooses based on its own execution state and any signals it observes on the channel. Initiators do not publish lifecycle events beyond `x-ably-run-start`.

Opening the run before any agent has responded decouples the request from its execution. Once `x-ably-run-start` is on the channel, the run is durable state that any agent can act on at any time. An agent can be invoked immediately, later, or repeatedly (e.g. for retries after HTTP invocation failure or durable-execution re-runs) without the initiator needing to republish anything. Concurrent invocations of the same run are harmless: the step layer serialises them via total order, so only one step wins at a time and duplicates close with `x-ably-step-end` carrying `x-ably-status: superseded`.

#### Server-side input validation

The default pattern is for the client to publish `x-ably-run-start` and its input message directly to the channel. This works when any authenticated client is trusted to contribute to the conversation. When a developer needs to enforce business logic, authorization, or input validation before accepting user input, they can route the client's message through a backend request handler instead.

In this pattern the client sends its input to the developer's backend (e.g. a REST endpoint or serverless function) rather than publishing to the channel. The handler performs whatever checks are needed — content moderation, validation, preprocessing — and, if the input is accepted, publishes both `x-ably-run-start` and the user's message to the channel on the client's behalf. The handler sets `x-ably-client-id` to the end-user's clientId on both publishes so that other participants observing the channel see the run as owned by the user, not by the backend connection that published it.

#### Client control signals

The run is the unit of live control — abort, pause, resume, and retry all target a run, as does steering when a user provides mid-run input. When a user hits stop, they stop the whole task, not a specific step or stream.

Clients (and other external initiators) influence execution by publishing durable messages to the channel that the agent observes and responds to. Abort closes the run terminally. Pause suspends it. Resume un-suspends it. Retry redoes work. Steering provides additional input. See [Control Signals](#control-signals) and [Steering](#steering) for the full treatment of each.

#### Concurrency

Multiple runs can be open simultaneously on a session, independent of each other. Each has its own ID (generated by its initiator), lifecycle, and sequence of steps, with no ordering constraint between runs.

A client can send a follow-up while the first response is still streaming. A parent agent can spawn subagent runs in parallel. A session can carry concurrent activity from multiple independent requests.

Concurrent work within an agent — such as an orchestrator fanning out to multiple subagents — is modelled as concurrent runs. Each subagent operates in its own run with its own sequential step chain. When a parent run is aborted, the orchestrator is responsible for cascading cancellation to the subagent runs it created. More generally, the invoker of a run is responsible for cleaning up the runs it invoked.

### Steps

A step is the abstraction below the run. It exists because the protocol needs a way to identify "one execution attempt" so that:

- Failed or abandoned output can be distinguished from successful output.
- Retries can be cleanly separated from original attempts.
- Durable-execution stages have a natural boundary.

Every agent-published message carries the step ID in `message.extras` as `x-ably-step-id`, so the output of a step can be identified and filtered purely by looking at the channel, with no coordination.

Concretely, a step is one continuous stretch of agent execution within a run: the unbroken work done by a single process from when it begins acting on the run until its execution ends. A step opens with `x-ably-step-start` and either closes with `x-ably-step-end` or is left open (e.g. due to abrupt termination), which is later resolved by the abandonment rule.

In the common case, a run has one step. An agent picks up the invocation, does its work (tool calls, reasoning, output), and finishes. Multiple steps appear when work must span several executions:

- HITL approvals: the agent finishes, the run suspends, a later step resumes after input arrives.
- Retries after failure: the first attempt fails, a new step tries again.
- Durable-execution workflows: each scheduled stage runs as its own step.

Every step in a run carries the same `x-ably-run-id`. Every message an agent publishes within a step carries both `x-ably-run-id` and `x-ably-step-id` in `message.extras`.

#### Lifecycle events

Two events bracket a step. Both are published by the agent and carry both `x-ably-run-id` and `x-ably-step-id` in `message.extras`.

##### `x-ably-step-start`

Opens a step. The step ID is generated by the agent at this moment and appears on the channel for the first time here as `x-ably-step-id` in `message.extras`.

##### `x-ably-step-end`

Closes a step. Carries `x-ably-status` in `message.extras` with one of:

- `complete`: the step finished its work. The run may or may not be done. A step that produces a tool call and then suspends the run is `complete`. A step that produces the final answer is also `complete`.
- `failed`: the step failed due to a stream error, model error, tool error, or timeout. The run is not necessarily over. A new step can retry.
- `aborted`: the step was stopped because an `x-ably-abort` request was observed on the channel during execution (see [Control Signals](#control-signals)). The agent then publishes `x-ably-run-end` with `x-ably-status: aborted` to close the run.
- `paused`: the step was interrupted by an `x-ably-pause` request observed on the channel during execution, and the step implementation supported mid-execution interruption (e.g. a LangChain interrupt). See [Client control signals](#client-control-signals). Publishing this status is an implementation choice: step runners that cannot be interrupted mid-execution run to completion and publish `complete` instead.
- `superseded`: the step observed an earlier concurrent `x-ably-step-start` for the same run (see [Sequentiality](#sequentiality)) and conceded the race. No error occurred. Distinct from `failed` because the step's output should not be treated as an execution failure for telemetry or client-side retry policy.

Step-level non-terminal halt is pause-caused only. A step that ends because the run is awaiting HITL input (a tool-call approval, a follow-up user message, or any other external input the codec domain defines) ends `complete`. The HITL state is signalled at the run level by `x-ably-run-suspend` with `x-ably-status: awaiting-input`, not at the step level.

#### Sequentiality

Steps within a run form a canonical sequence, ordered by `x-ably-step-start` serial, with at most one step considered current at any point. This is enforced by total order, not a distributed lock.

When an agent starts a step, it publishes `x-ably-step-start` and monitors its subscription. If it observes an earlier `x-ably-step-start` (by serial) for the same run with no `x-ably-step-end`, it has lost a race. It publishes `x-ably-step-end` with `x-ably-status: superseded` and stops. The earlier-serial `x-ably-step-start` wins, often without its agent ever knowing a race occurred.

Sequentiality lets the protocol avoid runtime coordination in the following cases:

1. **Crash detection without heartbeats or timeouts.** A crashed agent leaves a `x-ably-step-start` with no `x-ably-step-end`. Because only one step in a run can be active at a time, a later `x-ably-step-start` in the same run is unambiguous proof the prior step is no longer running, so materialisation treats the open step as abandoned as soon as the next `x-ably-step-start` appears. If concurrent steps were permitted, an open step could simply be a still-running sibling, and the protocol would need presence or heartbeat signals to distinguish a crash from live work.

2. **Safe handling of duplicate executions.** A task may be re-executed — a client retries or invokes twice, or a durable-execution framework automatically re-schedules a step. The new agent cannot rely on a pre-check to avoid running — eventual consistency means another agent's `x-ably-step-start` may not have reached its subscription yet. Sequentiality collapses the resulting concurrent attempts to a single authoritative step via total order.

#### Step abandonment

An agent process can terminate abruptly — crash, timeout, killed — without publishing `x-ably-step-end`. The step is left open on the channel: a `x-ably-step-start` with no corresponding `x-ably-step-end`. This is visible in the session. Any participant materialising the session can see that the step was never closed.

#### Run abandonment

A run can be left open without a terminal lifecycle event — the agent crashes before publishing `x-ably-run-end`, or no agent ever picks up the run. The run is left open on the channel: a `x-ably-run-start` with no corresponding `x-ably-run-end`. This is visible in the session. Any participant materialising the session can see that the run was never closed.

## Invocation

An invocation is the HTTP request that asks an agent to handle a run. Its payload declares a set of preconditions — events that must be visible on the channel before the agent begins — plus the channel where those events live. Once every precondition resolves, the agent reads the session and decides what to do from the state it finds there. The invocation never instructs a specific action; it only narrows the channel to a point where the agent can make that decision.

This split — "what channel state must be visible" carried in the invocation, "what to do given that state" decided by the agent from the session — is the key framing. Two properties follow: agent activity is driven entirely by state visible on the channel, and every piece of required input is published to the channel exactly once, never duplicated by a repeated HTTP request.

Invocations are infrastructure, not session state: they are not published to the channel, have no lifecycle, and carry no identity. An invocation is only used at the boundaries where an external initiator starts, retries or resumes work — durable-execution frameworks and long-lived agents drive internal progress from channel state alone.

### Preconditions

Preconditions are event IDs the agent waits to see in the session.

- **Channel name.** Where the session lives. The agent subscribes here and hydrates from history.
- **Run ID.** Always present. The agent waits for `x-ably-run-start` with this ID. This both establishes that the run has been opened and scopes the invocation to it.
- **Step ID.** Optional. The agent waits for `x-ably-step-start` with this ID to be visible. Used when an external initiator targets a specific prior step — typically a step runner with resumable checkpoint state that needs the new agent to pick up from a known point.
- **Message ID.** Optional. The agent waits for a specific message to be visible. Used when the invocation is paired with a message publish the agent must observe — most commonly the user's input for a new run, a HITL approval, or a control signal (e.g. `x-ably-resume`, `x-ably-retry`, `x-ably-abort`, `x-ably-pause`).

The invocation carries no message content or conversation history.

### Scenarios

The same invocation mechanism covers a range of initiator intents. In each case the invocation declares preconditions, and the agent decides what to do from session state once they resolve.

- **User message triggers a new run.** The client publishes `x-ably-run-start` and the user's message, then invokes with the run ID and the user message's ID.

- **HITL resumption after tool-call approval.** The prior step ended `complete` and the run is suspended with `awaiting-input`. The client publishes the approval as a message and invokes with the run ID and the approval message's ID. In codecs that represent the approval as an in-place state change on the existing assistant message (the same-ID republish path; see `ClientRun.sendMessages`) — e.g. the Vercel codec for AI SDK v6 — publishing the approval means republishing that assistant message with the same ID and the updated state; the invocation's `messageId` targets that original ID, and the republish is what the new step waits to see.

- **Explicit retry of a run.** The initiator publishes an `x-ably-retry` control message (see [Control Signals](#control-signals)) targeting the run, then invokes with the run ID and the retry signal's message ID.

- **Explicit retry of a specific step.** The initiator publishes an `x-ably-retry` control message (see [Control Signals](#control-signals)) targeting the run and carrying the failed or abandoned step's ID, then invokes with the run ID, the step ID, and the retry signal's message ID.

- **Resume of a paused run.** The run is suspended with `paused`. The initiator publishes an `x-ably-resume` control message (see [Control Signals](#control-signals)) targeting the run, then invokes with the run ID and the resume signal's message ID.

- **Resume of a paused step.** The prior step ended `paused`. The initiator publishes an `x-ably-resume` control message (see [Control Signals](#control-signals)) targeting the run and carrying the step ID, then invokes with the run ID, the step ID, and the resume signal's message ID.

Some channel publishes do not themselves require an invocation. **Abort** and **pause** (see [Control Signals](#control-signals)), together with **steering** (see [Steering](#steering)), are handled by a live agent directly on its subscription; with no live agent they wait on the channel until a later signal — typically resume or retry — wakes one. **Durable-execution framework retries** are driven by the framework's own scheduling and do not produce SDK-level invocations.

## Control Signals

Clients (and other external initiators) influence running work by publishing durable control messages to the channel. The agent observes these messages on its subscription, or discovers them when it hydrates the session, and responds according to the signal type. Four control signals are defined: abort, pause, resume, and retry.

All are durable channel messages carrying the target run ID in `message.extras` as `x-ably-run-id`; resume and retry may additionally carry `x-ably-step-id`. An initiator can publish any of them at any point regardless of whether an agent is currently live. A live agent observes and responds at its next opportunity. If no agent is running, the message is on the channel and available when the next step hydrates the session — and for signals that need an agent to produce an effect (abort, resume, retry, and pause when no live agent is present to emit `x-ably-run-suspend`), the initiator typically pairs the signal with an invocation that wakes one up.

### Abort

The initiator publishes an `x-ably-abort` control message to abort a run. The agent observes it, closes any step in progress with `x-ably-step-end` carrying `x-ably-status: aborted`, and publishes `x-ably-run-end` with `x-ably-status: aborted` to close the run terminally.

Abort is a content-free control signal. It carries no domain content — only the target run ID.

### Pause

The initiator publishes an `x-ably-pause` control message to pause a run. The agent observes it and eventually publishes `x-ably-run-suspend` with `x-ably-status: paused`, and does not start a new step. The run remains open and resumable. A later `x-ably-resume` signal (see below), paired with an invocation, wakes a new step.

What happens to a step in progress is an implementation choice of the step runner:

- If the step cannot be interrupted, it runs to completion and ends with `x-ably-step-end` carrying `x-ably-status: complete`. The agent then publishes `x-ably-run-suspend` with `x-ably-status: paused`. This is the default for most step implementations.
- If the step supports mid-execution interruption (for example, a LangChain interrupt), the agent stops the step immediately, publishes `x-ably-step-end` with `x-ably-status: paused` to mark the step's output as partial, and then publishes `x-ably-run-suspend` with `x-ably-status: paused`.

Either way, the effect on the run is the same: it suspends until `x-ably-resume` produces a new `x-ably-step-start`.

Pause is a content-free control signal. It carries no domain content — only the target run ID.

### Resume

The initiator publishes an `x-ably-resume` control message to un-suspend a run. It targets a run ID and optionally carries a step ID (`x-ably-step-id` in `message.extras`) when resumption is from a specific prior step's checkpoint. The agent observes the signal and starts a new step to continue the run.

Resume's job is typically to wake a run that is suspended and has no live agent (`paused`, `awaiting-input`, or with its last step ended `paused`), so it is almost always paired with an invocation. The invocation's preconditions wait for the resume signal to be visible and, if a step ID is carried, for that step's `x-ably-step-start`. With both in the session, the agent reads state and fulfils the resume — starting fresh for a paused run, or picking up from the checkpoint for a paused step.

Resume is a content-free control signal. It carries no domain content — only the target run ID and optional step ID.

### Retry

The initiator publishes an `x-ably-retry` control message to retry work on a run. It targets a run ID and optionally carries a step ID (`x-ably-step-id` in `message.extras`) to scope the retry to one specific prior step; without a step ID, the retry is run-level and the agent redoes work from the latest state of the run. The agent observes the signal and starts a fresh step with a new step ID; sequentiality resolves any race against an older step not yet observed to end.

Retry is produced by external systems — an orchestrator, a monitoring service, a user action — after observing a failed run or step (`x-ably-step-end` with `x-ably-status: failed`, or an `x-ably-step-start` with no terminal event from an abandoned worker). Durable-execution frameworks do not use the retry signal; they re-drive the agent internally from framework state without producing SDK-level channel signals.

Like resume, retry typically requires a wake-up invocation, whose preconditions wait for the retry signal and, if a step ID is carried, for that step's `x-ably-step-start`.

Retry is a content-free control signal. It carries no domain content — only the target run ID and optional step ID.

## Steering

Steering is how a client provides mid-run input to an ongoing run: a regular user message published to the channel carrying the target run's ID in `message.extras` as `x-ably-run-id`. Unlike a control signal, it carries actual content — encoded by the codec and decoded like any other user message — that the agent incorporates into its next model call.

The agent picks up steering input at its next iteration boundary. In a typical agent loop (model → tool → model → ...), the natural checkpoint is between iterations, when the agent reads the session before constructing the next model call. The new user message appears in the session alongside the conversation so far, and the agent includes it. The exact integration point is framework-specific; the protocol's role is to ensure the message is on the channel, scoped to the run, and available in the session when the agent next reads it.

If no agent is currently live on the run — it was paused, its last step ended `awaiting-input`, or the runtime is serverless — the steering message sits on the channel until a later step picks it up. Steering itself is not tied to an invocation; waking a fresh agent is a separate concern addressed by `x-ably-resume` or `x-ably-retry` (see [Control Signals](#control-signals)) and the invocation that accompanies them. The steering message contributes to the run's state once visible, regardless of which signal eventually wakes the agent.
